## 맥락

Java·Spring 백엔드에서 데이터 조회·저장 방식과 Repository 작성 기준을 통일해야 한다.
작업 요청자가 JPA 사용 방향을 제시했고, JPA를 기준으로 Repository·Entity 작성 방식을 통일하기로 했다.

## 결정

기본 DB 접근은 Spring Data JPA를 사용한다. DB 구조 생성·변경은 JPA 자동 변경이 아닌
[Flyway](0009-flyway-schema-migrations.md)가 담당한다. 실제 DB 환경·버전과 공간 데이터 매핑은
별도 초기 구성에서 검증한다. 이 결정만으로 런타임 DB 제품·버전까지 확정하지 않는다.

합의 근거: 본 업무 대화에서 Gradle(`build.gradle`)·JPA·Flyway 조합을 제안했고,
작업 요청자가 “좋은 것같아”로 동의했다. 결정 당시에는 실제 설정·실행 검증 전이었다. 같은 업무의 초기 구성에서 전체 빌드(`clean build`)로 확인했다.

## 고려한 대안

다른 ORM이나 SQL 매핑 프레임워크와의 상세 비교·성능 실험은 수행하지 않았다.
기존 JPA 작성 방식 재사용과 작업 요청자의 사용 의사를 근거로 선택했다.
DB 고유 기능·대량 처리에 필요한 직접 SQL은 JPA의 전면 대체가 아니라 해당 조회 목적에 따라
검토하며, 선택 기준은 백엔드 컨벤션을 따른다.

## 결과

- **얻는 것**: Repository·Entity 작성 방식 통일, 기존 작성 규칙 재사용
- **감수하는 것**: 연관관계 조회 성능, 트랜잭션 경계와 영속성 컨텍스트 관리 필요
- **후속 작업**: 의존성·DB 연결 설정과 빈 DB 통합 테스트는 초기 구성에서 완료했다.
  UUID·공간 데이터·제약 매핑과 그 통합 테스트는 Entity 구현 시 진행한다.
  개별 기능의 잠금·격리 수준을 이 결정으로 일괄 확정하지 않는다.
