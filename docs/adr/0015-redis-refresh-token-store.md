# ADR-0015: Refresh Token과 로그인 계열 상태는 Redis에 저장한다

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-10-28 |
| 결정자 | 작업 요청자(본 대화에서 Redis 선택 및 결정에 따른 문서 반영 요청) |
| 관련 | [S15P31E105-192](https://ssafy.atlassian.net/browse/S15P31E105-192), [S15P31E105-194](https://ssafy.atlassian.net/browse/S15P31E105-194), [ADR-0014](0014-common-api-authentication.md), [인증 계약](../design/api/users.md#갱신-권한-저장소), [데이터 모델](../design/db/erd.md#인증-저장소-경계) |
| 대체 관계 | —. ADR-0014의 미정 저장소를 구체화하며 기존 JWT 정책을 유지한다. |

후속 결정: [ADR-0017](0017-redis-login-attempt-store.md)에서 193번 로그인 실패 횟수·잠금 상태도 기존 인증용 Redis에 저장하도록 별도로 확정했다. 아래 결정 당시의 범위와 맥락은 보존하며, 이 문서의 Refresh Token 결정은 계속 유효하다.

## 맥락

RunWay는 러닝 중 앱 접속을 유지하며 운동 데이터를 저장·조회한다. Access Token은 최대 10분이고 갱신 권한은 최초 로그인부터 최대 30일이다. 활동 중인 로그인은 토큰 갱신을 반복하므로, 동시 러닝 사용자 증가에 따른 갱신 상태 처리와 운동 데이터 처리를 분리할 필요가 있다.

일반 회원 API의 JWT 검증은 Refresh Token 저장소를 조회하지 않는다. API 요청 수 자체를 갱신 요청 수로 계산하지 않으며, 실제 갱신 트래픽·병목·성능 개선 수치는 아직 측정하지 않았다. 사용자 상태 확인에 PostgreSQL이 필요할 수 있어 인증 전체의 DB 의존성이 없어지는 결정도 아니다.

작업 요청자는 PostgreSQL과 Redis의 성능·만료 관리·정합성·복구 차이를 비교한 뒤, 서비스 특성과 짧은 Access Token 수명에 따른 갱신 부하 분리를 이유로 Redis를 선택했다. 기존 PostgreSQL 저장안은 미승인 플랜의 제안이었으며 채택된 기술 결정을 대체하는 것은 아니다.

## 결정

Refresh Token의 해시와 로그인 계열·사용·폐기 상태 및 재사용 탐지에 필요한 교체 이력을 **Redis를 기준 저장소로 하여 관리**한다. 사용자·비밀번호 해시·러닝 프로필과 운동 데이터는 기존 PostgreSQL을 사용한다. 토큰 상태를 PostgreSQL에 중복 저장하거나 자동 대체하는 구성은 이번 선택에 포함하지 않는다.

- Redis는 갱신 권한을 판정하는 저장소다. 인증 데이터를 유실해도 되는 일반 캐시로 취급하지 않는다. 외부 동작과 토큰 수명·이력 보관 범위는 [U01~U03](../design/api/users.md#인증-정책-적용-범위)을 따른다.
- 만료 정리에는 TTL을 활용하되 모든 계열·토큰 이력의 만료 기준은 최초 로그인의 절대 만료시각이다. 교체할 때 30일을 새로 부여하지 않는다. 정확한 키·자료구조·만료 설정 명령은 후속 설계 대상이다.
- 교체·재사용 탐지·계열 폐기는 Redis 안에서 조건 확인과 상태 변경의 순서를 원자적으로 보장하도록 구현한다. 구체적인 스크립트·명령과 오류 처리는 후속 설계·검증으로 확정한다. 원자적 실행이 디스크 보존이나 PostgreSQL과의 공동 롤백까지 보장하지는 않는다.
- Redis 장애를 인증 성공이나 토큰 미존재로 바꾸지 않는다. 저장·판정을 확인할 수 없을 때의 외부 응답은 기존 503 계약을 따른다.
- 영속화·복구 후 이미 사용·폐기한 권한이 다시 허용되는 위험과 메모리 부족에 따른 인증 상태 손실을 다뤄야 한다. 허용 가능한 데이터 유실 범위와 실제 설정은 아직 승인하지 않았다. 이를 정하고 검증하기 전 영속 저장·안전한 복구가 완료됐다고 판단하지 않는다.

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| Redis를 갱신 권한 저장소로 사용 (선택) | 메모리 중심의 키 조회·조건부 변경, TTL 만료 관리, 운동 데이터 DB와 갱신 상태 처리 부하 분리 | 별도 영속화·메모리·장애 복구 설계, 교체 이력의 메모리 비용, PostgreSQL 사용자 상태와의 교차 저장소 정합성 처리 필요 |
| 기존 PostgreSQL에 계열·토큰 테이블 추가 | 사용자 상태와 토큰 변경을 같은 트랜잭션으로 처리 가능, 관계·이력 조회와 내구성 관리에 적합 | 갱신 쓰기가 운동 데이터와 DB 자원을 공유하고 만료 행 정리가 필요. 어느 수준에서 병목인지 실측 필요 |

## 결과

- **얻는 것**: 지속적인 로그인 갱신 상태를 운동 데이터 저장과 분리하고, 만료가 정해진 인증 데이터에 Redis의 키 기반 처리와 TTL을 활용한다. 성능 향상은 기대 효과이며 실측 결과가 아니다.
- **감수하는 것**: Redis가 로그인·갱신·로그아웃의 필수 의존성이 된다. 사용자 상태 변경과 토큰 저장을 일반적인 PostgreSQL 트랜잭션 하나로 묶을 수 없다. Redis 장애 중에도 기존 JWT의 서명 검증은 가능하지만 각 API의 다른 의존성이 동작한다는 보장은 아니다.
- **후속 작업**: 192번에서 Redis 키·계열·최초 토큰 해시 저장 모델, 버전·클라이언트, 실행·테스트 구성과 실패 처리를 설계하고 플랜 승인을 거쳐 구현한다. 194번은 이를 바탕으로 회전·재사용 탐지·로그아웃을 구현한다. 교체 이력은 계열의 절대 만료까지 유지하고, 동시 갱신·로그아웃 및 복구 후 권한 부활 여부를 검증한다. 탈퇴와 발급·갱신 사이의 순서, 중간 실패·결과 불확실성 처리도 먼저 확정한다.
- **미확정 설정**: AOF/RDB·디스크 반영 주기, 복제·장애 전환 및 복구 정책, 메모리 상한·퇴출 정책, 타임아웃·연결 관리, 네트워크·인증·Secret 주입은 실행 구성 단계에서 결정한다. 재시작·장애·용량 부족 테스트 없이 설정만으로 기존 보존 계약을 충족했다고 보고하지 않는다. 193번 로그인 실패 제한의 저장소는 이번 결정으로 변경하지 않는다.
- **재검토 조건**: 측정 결과 갱신 부하 분리 효과가 작거나, 필요한 보존·복구 보장을 Redis 구성으로 충족하기 어렵거나, 교체 이력의 메모리 비용이 커지면 PostgreSQL 등 대안을 새 ADR로 재검토한다.

## 기술 참고

확인일: 2026-10-28. 저장소의 PostgreSQL은 17이며, Redis와 클라이언트 버전은 아직 미정이다. Redis는 Context7 `/redis/docs` 조회 및 최신 공식 문서를 확인했다. 아래 자료는 설계 참고이며 특정 Redis 버전의 구현·성능·장애 복구 검증을 뜻하지 않는다.

- [Redis 원자적 스크립트 실행](https://redis.io/docs/latest/develop/programmability/eval-intro/): 다른 요청과의 실행 격리. 실패 시의 상태 보장과 내구성은 별도로 설계해야 한다.
- [Redis 영속화](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/): AOF 디스크 반영 정책에 따른 지연·데이터 유실 절충.
- [Redis 복제](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/): 비동기 복제와 장애 전환의 보장 한계. WAIT만으로 강한 일관성을 보장하지 않는다.
- [Redis 메모리 퇴출 정책](https://redis.io/docs/latest/develop/reference/eviction/): 인증 상태의 조기 퇴출과 쓰기 실패 정책 검토.
- [PostgreSQL 17 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html), [커밋 내구성](https://www.postgresql.org/docs/17/wal-async-commit.html): 비교 대안의 트랜잭션·보존 특성.
