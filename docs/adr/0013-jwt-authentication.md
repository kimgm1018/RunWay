# ADR-0013: 짧은 JWT와 갱신 토큰으로 로그인 유지와 로그아웃을 처리한다

| 항목 | 값 |
|---|---|
| 상태 | 대체 |
| 결정일 | 2026-10-27 |
| 결정자 | 작업 요청자(본 대화에서 정책 선택 및 ADR 작성 승인) |
| 관련 | [S15P31E105-190](https://ssafy.atlassian.net/browse/S15P31E105-190), [인증 API U01~U03](../design/api/users.md), [공통 API 규약](../design/api/README.md), [데이터 모델](../design/db/erd.md) |

대체됨: [ADR-0014](0014-common-api-authentication.md). 아래는 당시 결정 기록이며 현재 공통 인증 정책은 후속 ADR을 따른다.

## 맥락

RunWay는 건강·GPS 기록을 계정과 연결해 다루며, 운동 중 인증 만료 때문에 반복해서 로그인하거나 기록이 유실되는 상황을 피해야 한다. 현재 단일 서비스 백엔드를 기준으로 인증 보안과 구현·운영 비용을 함께 고려한다.

초기 논의에서는 로그아웃 즉시 Access Token을 차단하기 위해 모든 보호 요청에서 서버 로그인 상태를 조회하는 안을 검토했다. 이후 작업 요청자는 전문가 상담을 바탕으로 비용과 잔여 위험을 재검토하고, 2026-10-27 본 대화에서 “현실적인 후보로 얘기해준걸로 지금 결정할게. 그리고 adr 문서에도 작성해줘”라고 승인했다. 승인 대상은 JWT Access Token 10분, 최대 30일 로그인 유지, 로그아웃 시 Refresh Token 폐기다. 이전 즉시 차단 요구와 7일·14일 유지기간 제안은 이번 결정으로 변경한다. 이전 안은 채택된 ADR이 없으므로 대체할 ADR은 없다.

HTTPS는 전송 중 도청·변조를 방어하지만 자원 접근 권한 오류나 저장소·로그 유출까지 방어하지 않는다. “HTTPS로 보안 문제의 95%를 해결한다”는 수치나 심박수 단독 노출은 항상 안전하다는 주장을 채택 근거로 삼지 않는다.

## 결정

Access Token은 유효기간 10분의 JWT를 사용하며, Refresh Token으로 자동 갱신해 로그인 상태를 최대 30일 유지한다. 로그아웃 시 앱의 토큰을 삭제하고 서버의 해당 갱신 권한을 폐기하되, 기존 Access Token의 즉시 차단 목록과 매 요청의 로그인 세션 상태 조회는 도입하지 않는다.

- 30일은 최초 로그인부터의 최대 유지기간이며 갱신으로 계속 연장하지 않는다. Access Token 만료 때마다 비밀번호를 요구하지 않는다. 로그인 유지 상한을 넘는 Access Token이 생기지 않도록 발급 만료시각도 상한 내로 제한한다.
- 서버는 JWT 서명·만료 등 검증을 수행한다. 로그아웃 완료 후에도 기존 Access Token은 남은 유효기간 동안 인증에 사용할 수 있으며, 최대 약 10분의 잔여 접근 가능성을 수용한다. 로그아웃은 이미 처리한 요청이나 내려받은 데이터를 소급 취소하지 않는다.
- Refresh Token의 서버 폐기를 완료한 뒤 로그아웃 성공으로 처리한다. 해당 갱신 권한으로 추가 Access Token을 발급할 수 없어야 한다. Refresh Token 상태 관리는 필요하며, 전체 인증 시스템이 무상태라고 설명하지 않는다.
- Refresh Token은 기기의 보호 저장소에 보관하고 서버에는 원문 대신 해시를 저장한다. 사용 시 교체하고 재사용을 탐지하는 방향을 채택한다. 갱신 권한 폐기 후에도 이미 발급된 Access Token은 만료까지 남는다는 한계는 동일하다.
- HTTPS, 토큰·비밀번호의 로그 노출 방지, JWT에 불필요한 개인정보를 넣지 않는 원칙을 적용한다. API의 기록 소유자·공개 범위·현재 동의 검사는 별도로 유지하며, 로그인 상태 조회 생략을 모든 DB 조회 생략으로 해석하지 않는다.
- 운동 시간에 맞춰 Access Token 수명을 늘리지 않는다. 기존 요구사항의 로컬 기록 보존·재연결 전송 흐름을 유지하며 인증 복구 후 서버 전송을 재개한다.

여기서 기간은 선택한 보안·편의 절충의 초기 정책값이지 외부 표준의 의무값이 아니다. 서명 알고리즘과 대칭/비대칭 키 방식, 비활성 만료기간, 다중 기기의 폐기 범위, 갱신 재사용·동시 요청·응답 유실의 상세 처리와 정확한 API·DB 계약은 이번 결정만으로 확정하지 않는다.

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| JWT 10분 + 갱신 권한 최대 30일, 로그아웃 시 갱신 권한 폐기 (선택) | 매 요청의 로그인 상태 조회 없이 JWT를 검증하며 자동 로그인 편의를 제공 | 로그아웃·갱신 권한 폐기 후에도 기존 Access Token의 잔여 접근 가능. 갱신 상태 저장·교체·재사용 처리는 필요 |
| JWT + 매 요청의 활성 로그인 상태 확인 | 로그아웃·분실 대응 시 기존 토큰을 즉시 차단 가능 | 상태 조회와 가용성 의존, JWT 키 관리와 세션 관리가 모두 필요 |
| 무작위 토큰 + 서버 세션 | 단일 백엔드에서 단순한 권한 폐기 모델을 제공 | 매 요청 상태 조회 필요. 이번 선택에서는 잔여 접근 위험을 수용하고 JWT 검증 방식을 사용 |
| 장기 Access Token만 사용 | 갱신 절차가 단순하고 로그인 요구가 적음 | 즉시 폐기 수단이 없으면 탈취된 Access Token의 사용 가능 시간이 길어짐. 한 달의 편의는 갱신 토큰으로 확보 |

## 결과

- **얻는 것**: 짧은 Access Token으로 단일 접근 토큰의 노출시간을 제한하고, 자동 갱신으로 운동 중 로그인 요구를 줄인다. 인증을 위한 매 요청의 세션 상태 조회·차단 목록 운영을 생략한다.
- **감수하는 것**: 유출된 Access Token은 로그아웃 후에도 만료까지 사용될 수 있다. Refresh Token까지 탈취되면 10분 TTL만으로 방어할 수 없으며 갱신 권한 보호와 재사용 대응이 필요하다. 이 결정은 즉시 로그아웃 무효화를 권고하는 OWASP 지침을 전부 충족한다고 주장하지 않는다.
- **후속 작업**: 190번에서 U01~U03과 공통 인증 규약의 예시·정책·미정 항목을 이번 결정에 맞추고, 저장 모델과 기기별 폐기 범위를 확정한다. 현재 API 문서는 검토용 초안이며 이 ADR 작성만으로 세부 계약 반영이나 구현이 완료된 것은 아니다. 191~194에서 검증·발급·갱신·로그아웃을 구현하고 만료 경계, 로그아웃 후 잔여 접근과 갱신 거절, 갱신과 로그아웃 경합, 재사용·응답 유실, 타인 기록 접근 거절을 검증한다. 서버와 앱의 인증 복구·미전송 기록 보존도 함께 검증한다.
- **재검토 조건**: 즉시 차단이 필요한 제품 요구, 실제 탈취 사고, 접근 데이터·권한의 민감도 확대가 생기면 서버 세션 검사나 차단 목록을 새 ADR에서 재검토한다. 회원탈퇴·동의 철회 등 개별 기능의 접근 제한을 이번 로그아웃 절충으로 완화하지 않는다.
