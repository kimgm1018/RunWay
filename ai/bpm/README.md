# RunWay 페이스→BPM 변환 모델 (개인 보폭 모델)

BPM 폐순환 코칭의 첫 단계다. MPC가 정한 안내 페이스를 **그 사용자가 그 페이스로 달릴 때의 케이던스**로 바꿔 목표 BPM(메트로놈 박자)을 만든다(요구사항 BPM-001, Jira S15P31E105-310).

```text
목표 페이스(속도 v) ──▶ 그 사람의 보폭 L(v) ──▶ 목표 BPM = 60 × v / L(v)
```

박자 하나에 한 걸음을 딛게 하므로 **목표 BPM = 목표 케이던스(spm, 양발 합 걸음/분)**다. 같은 페이스라도 사람마다 보폭이 달라 케이던스가 다르므로, 사람별 보폭을 알아야 한다.

이 문서는 데이터 수집·변환(1~2절), 탐색(4~6절), 모델(7절), 트레드밀 평가(8절), BPM 함수(9절), 실외 검증(10절), 개인 워치 기록 검증(11절), 큐 켠 기록 검증(12절), 서비스 적용 흐름(13절), 테스트(14절)를 정리한다.

## 한눈에 보기

| 사용자 상황 | 쓰는 것 | 케이던스 MAE (spm) |
| --- | --- | --- |
| 모두에게 같은 BPM (비교 기준) | 학습 데이터 평균 케이던스 | 10.2 |
| 처음 쓰는 사용자 | 평균 보폭 직선 | 7.7 |
| 처음 쓰는 사용자 + 키 | 키로 조정한 평균 직선 | 6.4 |
| 자기 기록 1개 | 평균 직선 + 베이지안 보정 | 4.7 |
| 자기 기록 2개 | 평균 직선 + 베이지안 보정 | 3.5 |
| (같은 사람 반복 측정 차이) | 노이즈 바닥 | 1.2 |

사람 단위 5-fold 교차검증, 공개 트레드밀 데이터 51명 기준이다(8절).

**실외(10절, 5명)에서는** 기록 없이 11.8 spm, 그 사람의 트레드밀 기록 5개로 보정해도 11.4 spm이었지만, **실외 구간 1개로 보정하면 2.8 spm**이었다. 트레드밀 prior는 출발점으로만 쓰고 실제 러닝 기록으로 보정해야 한다.

**실제 워치 기록(11~12절, 각 1명)에서는** 큐 없이 뛴 러닝 89회에서 평균 직선 5.66 → 최근 5회 + 첫 1분 보정 3.01 spm이었다. 큐(BPM)를 켜고 뛴 기록도 **BPM을 따라간 구간만** 쓰면 보정에 쓸 수 있었다(BPM으로 페이스 예측 오차 53.8 → 33.1초/km). 지난 기록은 최근 5회보다 최근 15~25회가 나아 서비스 기본값을 최근 20회로 바꿨다(11절 BPM-006). 이 결과로 정한 서비스 흐름은 13절에 있다.

**서비스 규칙(`target_bpm.py`)을 사람별로 그대로 채점하면(12절 BPM-008·009)** 큐 없이 뛴 사람의 케이던스는 2.79 spm(±5 안 86%), 큐 켜고 뛴 사람의 "이 BPM이면 몇 초/km"는 자기 지난 기록으로 보정해 51.6 → 27.2초/km였다. 기록 없는 새 사용자 1명은 평균 직선으로 16.4초/km였고, 첫 1분 보정은 도움이 되지 않았다. 평균 직선은 큐 켠 두 사람 모두 실제보다 느리게 예측해, 실외 기록으로 다시 맞추는 것이 다음 개선 후보다.

| `explore_speed_cadence.py` | 두 표를 합치고 사람별 속도-케이던스·속도-보폭 그래프와 직선 요약을 만든다 |
| `stride_model.py` | 보폭 모델: prior 학습(`fit_prior`), 베이지안 보정(`personal_offset`), 예측(`predict_cadence`) |

| `convert_personal.py` | Samsung Health 내보내기 → 페이스가 일정한 60초 구간의 속도·케이던스 표(날짜·GPS 없음) |
| `evaluate_personal.py` | 개인 기록으로 러닝이 쌓일수록 오차가 줄어드는지 시간순 평가(BPM-004), W&B 기록 |
| `evaluate_cued.py` | 워치 데모 앱 BPM 기록으로 큐 켠 기록 보정 평가(BPM-005), W&B 기록 |
| `evaluate_tuning.py` | 개인 기록으로 노이즈 σ와 지난 기록 반영 개수(최근 N회·감쇠 가중)를 고름(BPM-006), W&B 기록 |

| `stride_prior.json`, `stride_prior_height.json` | 서비스용 prior(키 없는 / 키 있는). 공개 트레드밀 51명으로 학습한 평균 직선·사람 간 차이·노이즈 숫자뿐이다 |
| `tests/` | 합성 데이터 단위 테스트 |

서비스에서 바로 쓸 수 있게 prior JSON 두 개만 이 폴더에 둔다. `evaluate.py`로 prior를 다시 학습하면 출력 폴더의 새 파일로 바꾼다. 원본 데이터, 개인 기록, 결과 표·그래프는 저장소 밖(예: `runway_data/bpm/`)에 두고 커밋하지 않는다.

## 1. 왜 공개 데이터인가

필요한 것은 **같은 사람이 여러 속도로 뛴 기록의 속도와 케이던스**다(심박은 필요 없다).

- FitRec에는 케이던스가 없다.
- 처음에는 팀원 개인 러닝 기록을 모으지 못했다.
- 그래서 속도와 걸음 시점이 함께 있는 공개 러닝 바이오메카닉스 데이터 두 개로 prior를 만든다. 이후 개인 워치 기록(11절)과 워치 데모 앱 BPM 기록(12절)으로 서비스 상황을 검증했다.

| 데이터 | 출처 | 라이선스 | 내용 |
| --- | --- | --- | --- |
| Fukuchi et al. (2017) | figshare [10.6084/m9.figshare.4543435](https://doi.org/10.6084/m9.figshare.4543435) (v5), 논문 [PeerJ 10.7717/peerj.3298](https://doi.org/10.7717/peerj.3298) | CC BY 4.0 | 트레드밀 2.5·3.5·4.5 m/s, 힘판 300Hz, 30초 |
| Baker et al. (2025) | Zenodo [10.5281/zenodo.16541185](https://doi.org/10.5281/zenodo.16541185) | CC BY 4.0 | 트레드밀(힘판)·실내 트랙·실외 러닝, IMU + 힘판, stride 단위로 잘린 파일 |

### 받은 뒤 남긴 파일

**Fukuchi** (102개 파일, 40MB)
- `39452932_RBDSinfo.txt`: 참가자 정보(키 등). 가장 최신 버전
- `RBDS###runT25forces.txt`, `runT35forces.txt`, `runT45forces.txt`: 속도별 힘판 신호
- 지운 것: forces 파일과 최신 참가자 정보를 뺀 나머지(마커 좌표·처리 결과 파일 등). 케이던스 계산에 필요 없다.

**Zenodo** (2,756개 파일, 220MB)
- `TM_FP/participant_*/speed_*/cadence_SS1`, `cadence_SS2`: 트레드밀에서 **본인이 편한 케이던스로** 뛴 stride 파일
  - 참가자 1~10: 3 m/s만
  - 참가자 11~15: 2·2.5·3·3.5·4 m/s
  - SS2는 3 m/s 반복 측정
- `OUT/participant_11~15`: 실외 러닝. 100m 직선 구간 파일(사람당 10개, 약 25초, 120Hz IMU, GPS 시계 속도). 10절에서 쓴다
- `DATA_README.md`
- 지운 것: 메트로놈으로 케이던스를 150~190으로 강제한 조건(자연 케이던스가 아님), `OG`·`OG_FP`(실내 트랙). 필요하면 Zenodo에서 다시 받는다. 강제 케이던스 조건은 BPM-005에서 확인해 봤지만 stride 시간과 stride 개수로 구한 결과가 서로 맞지 않아 쓰지 않았다(12절).

## 2. 변환 방법

두 데이터 모두 원본에 케이던스 숫자가 없다. 데이터마다 걸음 시점에서 케이던스를 계산하고, 같은 컬럼의 표로 맞춘다.

### Fukuchi: 힘 신호에서 착지 찾기

| 읽은 값 | 위치 | 용도 |
| --- | --- | --- |
| `Fy` (수직 힘, N) | forces 파일 컬럼 | 착지 검출 |
| 사람 번호·속도 | 파일 이름 (`T25` → 2.5 m/s) | `subject_id`, `speed_mps` |
| `Subject`, `Height` | `RBDSinfo.txt` | `height_cm` |

1. `Fy`가 200N 미만에서 200N 이상이 되는 프레임을 착지로 본다. 직전 착지와 30프레임(0.1초) 미만이면 노이즈로 버린다.
2. 착지 간격 중 중앙값의 0.7~1.3배를 벗어난 간격(착지 하나가 두 번 잡힌 경우 등)을 뺀다.
3. 케이던스 = 60 × 300 / 평균 착지 간격(프레임), 보폭 = 60 × 속도 / 케이던스

### Zenodo 트레드밀: stride 시간

| 읽은 값 | 위치 | 용도 |
| --- | --- | --- |
| `delta_time` (s) | stride 파일 컬럼 | 합 = stride 시간 |
| `speed` (m/s) | stride 파일 컬럼 | `speed_mps` |
| 참가자·SS1/SS2 | 폴더 이름 | `subject_id`, `session_id` |

stride 파일 하나는 한 발 기준 한 주기, 즉 **두 걸음**이다(파일 안 수직 힘에 착지가 한 번 있다).

1. stride 시간 = `delta_time` 합 (약 121Hz, 파일당 80~100줄)
2. 폴더 안 stride 시간 중 중앙값의 0.7~1.3배를 벗어난 것을 뺀다.
3. 케이던스 = 120 / 평균 stride 시간, 보폭 = 60 × 속도 / 케이던스

### 결과 표 형식

한 줄 = 한 사람이 한 속도로 뛴 측정 하나.

| 컬럼 | 설명 |
| --- | --- |
| `subject_id` | `F_RBDS001`(Fukuchi), `Z_P11`(Zenodo) |
| `session_id` | `F_RBDS001_T25`, `Z_P11_TM_3_SS1` |
| `setting` | `treadmill` |
| `speed_mps` | 속도(m/s) |
| `cadence_spm` | 케이던스(양발 합 걸음/분) |
| `stride_m` | 한 걸음 길이(m) |
| `n_steps`, `n_dropped` | 계산에 쓴 걸음 수, 이상해서 뺀 간격 수(검증용) |
| `height_cm` | 키. Fukuchi만 있다 |
| `source` | `Fukuchi` / `Zenodo` (합친 표에만) |

### 데이터 품질 확인

- **Fukuchi 중복 파일:** RBDS029·030·032는 세 속도 파일의 내용이 바이트 단위로 같다(MD5 동일). 어느 속도의 기록인지 알 수 없어 9개 파일을 모두 뺀다(`convert_fukuchi.py`가 자동으로 제외).
- **범위 밖 값은 빼지 않았다:** 케이던스 142.6(RBDS024, 2.5 m/s)과 223.4(RBDS028, 4.5 m/s)는 일반 범위를 벗어나지만 착지 간격이 일정해 실제 값으로 본다.
- **짧은 기록:** RBDS037의 3.5 m/s 파일은 13초뿐이라 걸음 수가 적다(39개). 값은 정상이다.
- **같은 사람 안에서 속도가 빨라지면 케이던스가 커지는지:** 3개 이상 속도가 있는 33명 모두 그렇다.

## 3. 실행

`ai/bpm/`에서 순서대로 실행한다. pandas·numpy·matplotlib·statsmodels가 필요하고, W&B 기록에는 wandb, 테스트에는 pytest가 필요하다.

**① 변환·탐색**

```bash
python convert_fukuchi.py <fukuchi 폴더> <출력 폴더>/fukuchi.csv
```

```bash
python convert_zenodo_tm.py <zenodo 폴더> <출력 폴더>/zenodo_tm.csv
```

```bash
python explore_speed_cadence.py <출력 폴더>
```

`<출력 폴더>`에 `all_treadmill.csv`, `speed_vs_cadence.png`, `speed_vs_stride.png`를 저장하고 요약을 출력한다.

**② 평가와 서비스용 prior 저장**

```bash
python evaluate.py <출력 폴더> --wandb
```

`all_treadmill.csv`로 5-fold 평가를 하고 `eval_predictions.csv`, `stride_prior.json`, `stride_prior_height.json`을 저장한다. `--wandb`를 빼면 W&B에 기록하지 않는다. W&B 키는 터미널 환경변수 `WANDB_API_KEY`로만 준다.

**③ BPM 계산**

```bash
python target_bpm.py . --pace 360
```

첫 인자는 prior JSON이 있는 폴더다. `.`이면 이 폴더에 있는 서비스용 prior를 쓴다.

```bash
python target_bpm.py . --pace 360 --height 170 --record 3.0 175 --record 2.5 168 --comfort 160 185
```

**④ 실외 검증 (10절)**

```bash
python convert_zenodo_out.py <zenodo 폴더> --check-treadmill
```

```bash
python convert_zenodo_out.py <zenodo 폴더> <출력 폴더>/zenodo_out.csv
```

```bash
python evaluate_outdoor.py <출력 폴더> --wandb
```

첫 명령은 같은 방법으로 구한 트레드밀 케이던스를 stride 시간 정답과 비교한다. 마지막 명령은 `all_treadmill.csv`와 `zenodo_out.csv`를 읽고 `eval_outdoor_predictions.csv`를 저장한다.

**⑤ 개인 워치 기록 (11절)**

```bash
python convert_personal.py <Samsung Health 내보내기 폴더> <출력 폴더>/personal_windows.csv
```

```bash
python evaluate_personal.py <출력 폴더> --wandb
```

개인 건강 데이터라 출력 폴더는 저장소 밖에 둔다. 변환기는 개수만 출력하고, 평가는 `stride_prior.json`과 `personal_windows.csv`를 읽어 `eval_personal_predictions.csv`를 저장한다.

**⑥ 큐 켠 기록 (12절)**

```bash
python evaluate_cued.py <워치 JSON 폴더> <출력 폴더> --exclude-date 2026-10-27 --wandb
```

워치 데모 앱 내보내기(UTF-8·UTF-16 JSON)를 읽는다. `--exclude-date`는 뺄 러닝의 시작 날짜(UTC)이고 여러 개 줄 수 있다. `eval_cued_predictions.csv`를 저장한다.

**⑦ 노이즈·지난 기록 개수 고르기 (11절 BPM-006)**

```bash
python evaluate_tuning.py <출력 폴더> --wandb
```

`stride_prior.json`과 `personal_windows.csv`를 읽어 `eval_tuning_grid.csv`(모든 조합의 앞 절반·뒤 절반 오차)를 저장한다.

**⑧ 서비스 규칙 그대로 채점 (12절 BPM-008·009)**

```bash
python evaluate_service.py <출력 폴더> --cued <워치 JSON 폴더> <참가자 ID> --cued <다른 사람 워치 JSON 폴더> <참가자 ID> --exclude-date 2026-10-27 --wandb
```

`personal_windows.csv`(큐 없이 뛴 사람)와 `--cued`로 준 사람별 큐 켠 기록을 **사람마다 따로** 시간순으로 채점하고 `eval_service_predictions.csv`를 저장한다. `--cued`는 사람마다 한 번씩 준다.

**⑨ 테스트**

```bash
python -m pytest -q tests
```

## 6. 탐색 결론

1. **사람별 보정이 필요하다.** 같은 속도에서 사람 간 케이던스 차이가 30 spm을 넘는다. 모두에게 같은 BPM을 주면 일부 사용자에게는 크게 어긋난다.
2. **보폭을 속도의 직선으로 모델링한다.** 보폭은 사람마다 거의 직선(R² 중앙값 0.998)이고 케이던스보다 직선에 가깝다. 보폭을 예측하고 BPM = 60 × 속도 / 보폭으로 바꾼다.
3. **절편과 기울기를 둘 다 사람별로 보정한다.** 둘 다 사람마다 다르다(절편 표준편차 0.10m, 기울기 0.04). 전체 평균 직선을 prior로 두고 사용자 기록으로 절편·기울기를 베이지안 보정하는 혼합효과 모델을 쓴다.
4. **기본 높이를 맞히는 것이 가장 중요하다.** 속도가 80% 빨라져도 케이던스는 약 14%만 변한다. 사람 간 차이(약 37 spm)가 속도에 따른 변화보다 크므로, 러닝 초반 자연 케이던스 하나로 보정하는 것만으로도 오차가 크게 줄 것으로 예상했다. 8절에서 7.5 → 4.7 spm으로 확인했다.

## 7. 모델

딥러닝이 아니라 **선형 혼합효과 모델(계층적 베이지안 선형 회귀)**이다. 데이터가 51명뿐이고 보폭이 속도에 대해 거의 직선이라, 숫자 몇 개만 학습하는 모델로 충분하다.

### 식

```text
보폭(m) = (μa + Δa) + (μb + Δb) × (속도 − 3)
BPM     = 60 × 속도 / 보폭      (속도 = 1000 / 페이스(초/km))
```

- μa, μb: 모든 사람의 평균 직선(3 m/s에서의 보폭, 1 m/s당 보폭 증가). 속도를 3 m/s 기준으로 옮겨 절편의 뜻을 분명하게 하고 절편·기울기 상관을 줄인다.
- Δa, Δb: 그 사람이 평균과 다른 정도. 사람 간 공분산 G를 따르는 정규분포로 본다.
- 측정마다 노이즈 σ²가 더해진다.

### 학습 (prior)

statsmodels `MixedLM`(REML)으로 `stride_m ~ v`, 그룹 `subject_id`, 랜덤효과 `~v`를 맞춘다(`fit_prior`). 결과는 μ, G, σ²뿐이고 `stride_prior.json`에 저장한다. "MLE may be on the boundary" 경고가 나오지만 수렴(`converged=True`)한다.

| | 키 없는 prior (51명) | 키 prior (Fukuchi 36명) |
| --- | --- | --- |
| μa (3 m/s 보폭) | 1.086 m | 1.073 m (키 175cm 기준) |
| μb (1 m/s당) | 0.281 m | 0.274 m |
| 키 계수 | – | 10cm당 +0.049 m (범위 162.7~192.4cm, 밖이면 잘라 씀) |
| 사람 간 표준편차 (절편 / 기울기) | 0.052 / 0.033 | 0.041 / 0.032 |
| 측정 노이즈 σ | 0.020 m | 0.024 m |

### 사용자별 보정

사용자 기록 k개(속도, 보폭 = 60 × 속도 / 케이던스)를 X(k×2, 행 [1, 속도−3]), y에 넣고 닫힌 공식으로 계산한다(`personal_offset`). 반복 학습이 없다.

```text
P = (G⁻¹ + XᵀX / σ²)⁻¹
(Δa, Δb) = P · Xᵀ (y − Xμ) / σ²
```

기록이 적으면 평균 쪽에 머물고, 많아질수록 그 사람의 직선으로 옮겨간다. 끌어당기는 정도는 G와 σ²의 비율로 정해진다.

## 8. 평가

### 방법 (`evaluate.py`)

- 사람 단위 5-fold(seed 42). fold마다 학습용 사람으로만 prior와 평균 케이던스를 다시 계산한다.
- 입력: `all_treadmill.csv`에서 SS2를 뺀 127행, 51명. SS2는 노이즈 바닥 계산에만 쓴다.
- 평가용 사람의 측정을 "보정용 / 예측 대상"으로 나눈다. 같은 시나리오(k) 안의 방법끼리만 같은 예측 대상을 비교한다.

| 시나리오 | 상황 | 비교한 방법 |
| --- | --- | --- |
| k0 | 그 사람 기록 없음, 모든 측정을 예측 (51명) | fixed, population, population_height |
| k1 | 측정 1개로 보정, 나머지 예측 (33명) | fixed, population, bayes_1, bayes_1_height |
| k2 | 측정 2개로 보정, 남은 1개 예측 (속도 3개 이상 33명) | fixed, population, bayes_2, own_line_2 |

- fixed: 학습 데이터 평균 케이던스 하나
- population: 평균 직선 μ
- bayes_k: 기록 k개로 베이지안 보정
- own_line_2: prior 없이 기록 2개로만 맞춘 직선
- *_height: 키 prior. 키를 모르는 사람(Zenodo)은 키 없는 prior로 대신한다.

사람당 측정이 최대 3개(Fukuchi)라 33명 전체로는 k2까지만 볼 수 있다. 서비스에서는 기록 수에 제한이 없다.

### 해석

1. **기록 1개로 보정하면 오차가 7.5 → 4.7 spm으로 37% 준다.** 러닝 초반 자연 케이던스로 보정하는 방식의 근거다.
2. **기록이 2개면 3.5 spm**까지 내려간다. 기록이 쌓일수록 좋아진다.
3. **보정 속도에서 멀어질수록 나빠진다**(1 m/s 4.4 → 2 m/s 6.6). 페이스가 크게 바뀌면 그 구간 기록으로 다시 보정하는 것이 좋다. 거리 0.5·1.5 m/s는 Zenodo 5명뿐이라 비교에서 뺐다.
4. **데이터별 차이는 모델 차이가 아니다.** Zenodo는 속도 범위가 좁고(2~4 m/s) 5명뿐이라 원래 쉽다(fixed도 더 낮다).
5. **own_line_2가 bayes_2보다 조금 낫다.** 실험실 데이터가 깨끗해 2점 직선도 잘 맞기 때문이다. 서비스는 기록 1개에서도 동작하고, 두 기록의 속도가 비슷하거나 흔들려도 직선이 크게 틀어지지 않는 bayes를 쓴다.
6. **키는 기록이 없을 때만 쓴다.** 기록이 없으면 7.69 → 6.40으로 좋아지지만, 기록이 생기면 약간 나빠진다(4.72 → 4.87). 키가 사람 간 차이를 일부 설명해 G가 작아지면서, 실제 기록 쪽으로 덜 움직이기 때문이다.

## 9. BPM 함수 (`target_bpm.py`)

`target_bpm(pace_sec_per_km, prior, prior_h=None, records=None, height_cm=None, comfort_range=None)`

| 상황 | 쓰는 prior | `source` |
| --- | --- | --- |
| 기록 1개 이상 | 키 없는 prior + 기록으로 베이지안 보정 (키 무시) | `bayes` |
| 기록 0개, 키 있음, 키 prior 있음 | 키 prior | `height_prior` |
| 그 외 | 키 없는 prior | `population` |

- `records`: 그 사용자의 (속도 m/s, 케이던스 spm) 목록. 저장된 구간에서 `select_records`로 골라 넣는다.
- 출력: `bpm`(정수), `raw_cadence`(제한 전 예측), `source`, `n_records`
- 제한 순서: 편한 범위(`comfort_range`) → 60~220 → 반올림
- 페이스가 0 이하이면 `ValueError`

예 (6:00/km):

| 입력 | BPM | source |
| --- | --- | --- |
| 기록·키 없음 | 163 | population |
| 키 160cm (162.7cm로 잘림) | 175 | height_prior |
| 키 190cm | 153 | height_prior |
| 기록 (3.0 m/s, 175) | 170 | bayes |
| 기록 (3.0, 175), (2.5, 168) | 171 | bayes |
| 편한 범위 165~180 | 165 | population |

기록·키가 없을 때 페이스별: 4:00 → 177, 5:00 → 169, 5:30 → 166, 6:00 → 163, 7:00 → 157, 8:00 → 151, 10:00 → 141.

### 보정 기록 고르기 (`select_records`)

`select_records(windows, recent_runs=20, follow_spm=5, speed_bin=0.25)`. `windows`는 저장된 구간 `Window(run_no, speed_mps, cadence_spm, cue_bpm)` 목록이고, 큐를 끈 구간은 `cue_bpm=None`이다.

1. 큐를 켰는데 |케이던스 − BPM| > 5 spm인 구간(BPM을 따라가지 않은 구간)을 뺀다(12절).
2. 쓸 구간이 남은 러닝 중 최근 20회만 남긴다(11절 BPM-006, 잠정값). 기록이 20회보다 적으면 전부 쓴다.
3. 러닝 × 속도 칸(0.25 m/s)마다 보폭 평균 하나로 묶는다. 한 러닝 안의 비슷한 구간이 과하게 반영되지 않게 하려는 것이다.

### 처음 사용자의 첫 1분 보정 (`first_minute_bpm`)

`first_minute_bpm(current_bpm, pace_sec_per_km, first_window, past_records, prior, ...)`. 이번 러닝의 페이스가 일정한 첫 1분으로 BPM을 한 번 다시 계산한다. 아래 경우에는 `None`(지금 BPM 유지)을 돌려준다.

- 보정에 쓸 지난 기록이 있는 사용자
- 첫 1분에 BPM을 따라가지 않았을 때
- 새 BPM이 지금 BPM과 3 spm 미만으로 차이 날 때(잠정값)

러닝당 한 번만 부르는 것은 호출하는 쪽에서 지킨다. 예(6:00/km, 처음 BPM 163을 따라 뛴 1분): 2.78 m/s면 그대로, 2.5 m/s면 166, 2.3 m/s면 169.

## 10. 실외 검증 (BPM-003)

트레드밀로 학습한 모델이 실외에서도 맞는지, 서비스에 맞는 보정 방법이 무엇인지 확인한다.

### 데이터와 케이던스 추출 (`convert_zenodo_out.py`)

- Zenodo `OUT` 참가자 11~15(5명), 400m 트랙의 100m 직선 구간 10개씩(50구간, 약 25초)
- 논문(Baker et al. 2025, PLOS ONE [10.1371/journal.pone.0330042](https://doi.org/10.1371/journal.pone.0330042)) 기준으로, 실외는 편한 속도·케이던스로 뛰었고 메트로놈은 없었다. 두 번째 1km에서는 200m마다 속도를 바꿨다. 속도는 GPS 시계 값이다.
- 실외에는 힘판이 없어서 **발 자이로의 주기(자기상관)**로 stride 시간을 찾는다.
  1. 발 자이로 세 축 중 가장 크게 흔들리는 축(다리 앞뒤 회전)을 고른다.
  2. 자기상관이 가장 큰 지연(0.45~1.1초)을 stride 시간으로 본다. 꼭짓점을 포물선으로 보정한다.
  3. 케이던스 = 120 / stride 시간, 속도는 구간 `speed` 중앙값(시작 직후 0인 줄 때문)
- **방법 확인:** 트레드밀 stride 파일 50개 폴더에 같은 방법을 적용해 stride 시간 정답과 비교했다. 평균 1.18 spm, 최대 1.84 spm 차이로 노이즈 바닥 수준이다. 실외 파일 하나는 가속도 크기·자이로 피크 세기로도 같은 값(약 157 spm)이 나왔다.
- 결과: 실외 속도 2.54~4.18 m/s, 케이던스 149~189 spm, 자기상관 0.94 이상

### 방법 (`evaluate_outdoor.py`)

평가할 사람은 prior 학습에서 뺀다(leave-one-subject-out, 50명으로 학습). 모델은 7절과 같고, 보정에 쓰는 기록만 바꾼다.

| 방법 | 보정에 쓴 기록 |
| --- | --- |
| fixed | 학습 데이터 평균 케이던스 |
| population | 없음 (평균 직선) |
| bayes_tm | 그 사람의 트레드밀 기록 5개(SS1, 2~4 m/s) |
| own_tm_line | prior 없이 그 사람의 트레드밀 기록만으로 맞춘 직선 |
| bayes_out_1 | 그 사람의 실외 구간 1개. 나머지 9개를 예측하고, 보정 구간을 바꿔 10번 반복 |
| bayes_tm_out_1 | 트레드밀 기록 5개 + 실외 구간 1개 |

### 결과 (실외 케이던스, spm)

| 방법 | 예측 수 | MAE | 치우침(예측−실제) | ±5 spm 안 |
| --- | --- | --- | --- | --- |
| fixed | 50 | 10.76 | +1.29 | 22% |
| population | 50 | 11.78 | +0.75 | 20% |
| bayes_tm | 50 | 11.43 | −2.75 | 18% |
| own_tm_line | 50 | 11.27 | −2.90 | 20% |
| **bayes_out_1** | 450 | **2.76** | −0.12 | **87%** |
| bayes_tm_out_1 | 450 | 9.15 | −2.58 | 28% |

같은 사람의 트레드밀 직선과 비교한 실외 케이던스 차이(실외 − 트레드밀, 같은 속도):

| 사람 | 차이 평균 | 구간 간 표준편차 | bayes_out_1 MAE |
| --- | --- | --- | --- |
| P11 | +5.9 | 1.9 | 1.68 |
| P12 | +21.0 | 2.1 | 1.98 |
| P13 | −15.9 | 1.9 | 2.61 |
| P14 | −5.1 | 2.5 | 2.93 |
| P15 | +8.6 | 2.9 | 4.58 |

### 해석

1. **그 사람의 트레드밀 기록은 실외로 옮겨지지 않았다.** 트레드밀 기록 5개로 보정해도 11.4 spm으로 평균 직선(11.8)과 비슷하다.
2. **트레드밀과 실외의 차이는 사람마다 방향과 크기가 다르다**(−16 ~ +21 spm). 그래서 "실외는 +몇 spm" 같은 일괄 보정은 안 된다. 대신 한 사람 안에서는 일정하다(표준편차 2~3 spm).
3. **같은 환경의 기록 1개로 보정하면 2.76 spm**이다(±5 안 87%). 한 사람 안에서 차이가 일정하기 때문에 기록 하나로 그 사람의 차이를 거의 잡는다. 서비스에서 러닝 초반 기록으로 바로 보정하는 설계의 근거다.
4. **다른 환경의 기록을 섞으면 나빠진다**(9.15). 트레드밀 기록 5개가 실외 기록 1개를 눌러버린다. 서비스에서도 오래된 기록이나 다른 환경의 기록보다 지금 러닝의 기록을 더 믿어야 한다.
5. 기록이 없을 때 실외 오차(11.8)는 트레드밀 평가(7.7)보다 크다. 첫 BPM은 꽤 틀릴 수 있으므로 초반 보정이 더 중요하다.

### 한계

- 실외 참가자는 5명뿐이라 2번은 "이런 경향이 있다" 정도로만 말할 수 있다.
- 실외 속도는 GPS 시계 값이라 조금 흔들릴 수 있다. 다만 21 spm 차이는 속도 오차(약 2 m/s 필요)로 설명되지 않는다.
- 트레드밀과 실외의 참가자 번호가 같은 사람인지는 논문에 명시되지 않았다(폴더 이름이 같아 같은 사람으로 봤다). 다른 사람이면 1·2·4번은 해석할 수 없다. bayes_out_1 결과는 실외 데이터만 쓰므로 이 문제와 상관없다.

## 11. 개인 워치 기록 검증 (BPM-004)

공개 데이터에는 한 사람이 여러 날 뛴 기록이 없다. 실제 워치 기록 1명으로 러닝이 쌓일수록 보정이 좋아지는지 확인한다.

### 데이터 (`convert_personal.py`)

- Samsung Health 내보내기의 러닝 기록(`exercise_type` 1002)에서 워치 `live_data`(약 10초 간격 속도·케이던스)를 읽는다.
- 60초 구간으로 나눠, 달리는 중(1.5 m/s 이상, 120~230 spm)이고 페이스가 일정한(속도 변동계수 ≤5%, 케이던스 표준편차 ≤5 spm, 기록 4개 이상) 구간만 평균을 낸다.
- 결과: 러닝 93회, 구간 1,519개. 속도 1.5~4.5 m/s(중앙값 2.83), 케이던스 중앙값 168 spm. 모두 큐 없이 뛴 기록이다.
- 개인 건강 데이터라 날짜·GPS는 저장하지 않고 시간순 러닝 번호만 남긴다. 결과 표는 저장소 밖에만 둔다.

### 방법 (`evaluate_personal.py`)

- **시간순 평가:** n번째 러닝의 구간을 예측할 때 1 ~ n−1번째 러닝 기록과 이번 러닝의 첫 구간만 쓴다(미래 미사용). 각 러닝의 첫 구간을 뺀 1,426구간(89회)을 예측한다.
- prior는 공개 트레드밀 51명으로 학습한 `stride_prior.json`을 그대로 쓴다.
- 지난 기록은 러닝 × 속도 칸(0.25 m/s)별 평균 하나로 묶는다.

| 방법 | 보정에 쓴 기록 |
| --- | --- |
| population | 없음 |
| bayes_inrun_1 | 이번 러닝 첫 구간(1분)만 |
| bayes_past | 지난 러닝 전부 |
| bayes_last5 | 최근 러닝 5회 |
| bayes_past_inrun | 지난 러닝 전부 + 첫 1분 |
| bayes_last5_inrun | 최근 5회 + 첫 1분 |

### 결과 (케이던스, spm)

| 방법 | MAE | 치우침 | ±5 spm 안 |
| --- | --- | --- | --- |
| population | 5.66 | −5.27 | 48% |
| bayes_inrun_1 | 3.41 | −1.83 | 77% |
| bayes_past | 3.25 | +0.76 | 79% |
| bayes_last5 | 3.20 | −0.32 | 81% |
| bayes_past_inrun | 3.20 | +0.73 | 80% |
| **bayes_last5_inrun** | **3.01** | −0.39 | **83%** |

지난 러닝 수별 MAE(population → bayes_last5_inrun): 0회 10.93 → 6.26, 1회 7.72 → 5.69, 2~4회 12.39 → 3.31, 5~9회 9.09 → 6.64, 10~19회 7.55 → 4.68, 20~49회 7.74 → 2.88, 50회 이상 4.26 → 2.75. 0~9회 칸은 러닝 수가 1~3회라 흔들림이 크다.

### 해석

1. **기록이 쌓일수록 좋아진다.** 지난 러닝이 20회 이상이면 약 2.8~3.2 spm이다.
2. **최근 5회가 전체 기록보다 조금 낫다**(3.20 vs 3.25). 10절처럼 오래된 기록보다 최근 기록이 더 잘 맞는다. 몇 회가 가장 좋은지는 BPM-006에서 다시 골랐다(아래).
3. **지난 기록이 없어도 첫 1분만으로 3.41**까지 내려간다. 처음 사용자에게 첫 1분 보정이 효과가 크다.
4. **기록이 있는 사용자는 첫 1분 효과가 거의 없다.** 지난 기록이 5회 이상인 러닝 84회에서 첫 1분 반영으로 예측이 바뀐 정도는 중앙값 0.23 spm이고, 3 spm 이상 바뀐 러닝은 1회였다(그 러닝은 오차 32.9 → 3.2).

### 노이즈와 지난 기록 개수 다시 고르기 (BPM-006, `evaluate_tuning.py`)

같은 개인 기록으로 두 가지를 바꿔 본다.

- **노이즈 σ:** 기록 하나를 얼마나 믿을지 정한다(작을수록 크게 보정). prior 값 0.02 m는 실험실 기준이라 0.005~0.10 m로 바꿔 본다.
- **지난 기록 반영:** 최근 5·10·15·20·25·30·40·50·60회, 전부, 감쇠 가중(λ^지난 러닝 수, λ = 0.5~0.95). 기록이 N회보다 적으면 있는 기록을 전부 쓴다.
- 과적합을 막으려고 **앞 절반 러닝(1~49번)으로 고르고 뒤 절반(50번 이후)에서 확인**한다. 기록 있는 사용자는 지난 기록만, 처음 사용자는 첫 1분만으로 보정한다.

노이즈를 나눠 보면 같은 러닝 안 구간끼리는 0.014 m(60초 평균이라 실험실 σ보다 작다), 러닝 간(날마다)은 0.027 m, 이 사람의 평균 직선과의 차이는 −0.030 m다. 평균과의 차이가 날마다 흔들리는 정도와 비슷해서, 몇 번의 러닝으로는 원래 차이인지 그날 차이인지 구분하기 어렵다.

결과 (기록 있는 사용자, 케이던스 MAE spm, σ 0.02):

| 최근 N회 | 앞 절반 | 뒤 절반 | 전체 |
| --- | --- | --- | --- |
| 5 (이전 기본값) | 3.57 | 2.95 | 3.18 |
| 10 | 3.32 | 2.66 | 2.90 |
| 15 | 3.01 | 2.61 | 2.75 |
| **20 (새 기본값)** | 2.99 | 2.67 | 2.79 |
| 25 | 2.94 | 2.85 | 2.89 |
| 30 | 3.11 | 2.99 | 3.03 |
| 50 | 3.31 | 3.14 | 3.20 |
| 전부 | 3.31 | 3.18 | 3.23 |

- **σ는 0.02 그대로 둔다.** 0.01~0.03 사이 차이는 0.05 spm 이내이고, 키우면 나빠진다. 처음 사용자 첫 1분 보정도 0.02가 가장 좋았다(뒤 절반 2.66).
- **지난 기록은 최근 20회로 바꾼다.** 5회는 너무 적어 그날 흔들림에 끌려가고, 30회 이상은 오래된 기록이 섞여 전부 쓰는 것과 비슷해진다. 앞 절반은 25회, 뒤 절반은 15회가 가장 좋아, 둘 다에서 상위인 20회를 골랐다(뒤 절반 2.95 → 2.67).
- 감쇠 가중(λ 0.8~0.9)도 비슷하게 좋지만 같은 효과면 단순한 최근 N회를 쓴다.
- 1명 기록이라 정확한 숫자보다 "10~25회 정도"라는 범위가 의미 있다. 실제 사용자 대부분은 처음 몇 달 동안 기록이 20회보다 적어 전부 쓰는 것과 같다.

### 경사 항 확인 (BPM-007)

오르막·내리막에서 같은 속도라도 보폭이 달라지는지, 보폭 모델에 경사 항(보폭 + c × 경사%)을 넣을지 확인했다. 경사 항을 넣지 않기로 해서 실험 코드는 저장소에 넣지 않고 방법과 결과만 기록한다.

- **경사 계산:** Samsung Health location_data의 약 1초 간격 고도만 읽었다(위도·경도는 쓰지 않고 저장하지 않았다). 60초 구간 안 고도를 시간에 대한 직선으로 맞춘 기울기(m/s)를 그 구간 속도로 나눠 경사(%)를 구했다. 고도 기록이 20개 미만이면 비워 뒀다. 고도는 30초 기준 흔들림이 약 0.14 m로 매끄러웠다.
- 1,519구간 중 1,514구간에 경사가 붙었다. 85%가 ±1% 안의 평지이고, |경사| ≥ 2% 구간은 81개다.
- **효과 크기:** 날마다 달라지는 보폭을 빼려고 러닝 평균을 뺀 잔차를 러닝 안 경사 편차에 회귀했다. 경사 1%당 보폭 −0.2 mm, 케이던스 약 +0.03 spm(2.83 m/s 기준)으로 측정 흔들림(1.2 spm)보다 훨씬 작다.
- **예측 비교:** 앞 절반 러닝(구간 기준 61번까지)으로 정한 계수(−0.5 mm/%)를 뒤 절반에 적용했다(최근 20회 보정, 지난 기록도 경사 몫을 빼고 보정).

| 구간 | 경사 없음 MAE | 경사 항 추가 MAE |
| --- | --- | --- |
| 전체 (712) | 2.57 | 2.57 |
| \|경사\| ≥ 2% (18) | 3.15 | 3.24 |
| −2% 이하 | 3.41 | 3.32 |
| 2% 이상 | 3.01 | 3.20 |

- **경사 항은 서비스에 넣지 않는다.** 오르막에서는 속도를 늦추는데 모델이 이미 속도에 따른 보폭 변화를 반영하고, 경사 구간이 적고 완만하다. 페이스가 일정한 구간만 쓰므로 페이스가 크게 흔들리는 언덕 구간이 빠졌을 수도 있다. 언덕 코스 기록이 쌓이면 다시 확인한다.
- 참고로 같은 기록에서 러닝 경과 시간(피로)에 따른 보폭 변화도 10분당 약 0.5 mm(케이던스 약 0.08 spm)로 작아 넣지 않는다.

## 12. 큐 켠 기록 검증 (BPM-005)

서비스에서는 대부분 큐(BPM)를 켜고 뛴다. 큐를 켜면 케이던스가 BPM 쪽으로 끌려가므로, 그런 기록으로도 보정할 수 있는지 확인한다.

### 데이터 (`evaluate_cued.py`)

- 워치 데모 앱 BPM 실험 기록(JSON, 1초 간격 `CADENCE`·`SPEED`와 그때의 목표 BPM). Runner01 5회, 모든 구간 큐(소리·진동) 켜짐.
- 10/27(UTC) 기록은 다른 사람이 Runner01로 뛴 기록이라 `--exclude-date`로 뺐다. Runner1의 1.7분 테스트 기록도 쓰지 않는다.
- 20초 구간마다 평균 속도·케이던스와 목표 BPM을 만든다. 구간 안에서 BPM이 바뀐 구간과 1.5 m/s 미만은 뺀다. 194구간이다.
- |케이던스 − BPM| ≤ 5 spm이면 **BPM을 따라간 구간**으로 본다.

### 방법

- 러닝 하나씩 빼고(leave-one-run-out), 나머지 러닝 기록으로 보정한다.
- 서비스가 알고 싶은 것은 "이 BPM을 주면 몇 페이스로 뛰나"다. 보정한 보폭 직선에 `60 × 속도 = BPM × (A + B × (속도 − 3))`을 넣고 속도를 거꾸로 풀어, 뺀 러닝에서 BPM을 따라간 159구간의 페이스와 비교한다.

| 방법 | 보정에 쓴 기록 |
| --- | --- |
| population | 없음 (평균 직선) |
| bayes_cued_all | 다른 러닝의 큐 켠 구간 전부 |
| bayes_cued_followed | 그중 BPM을 따라간 구간만 |

### 결과

BPM을 따라갔는지:

| 목표 BPM | 구간 수 | 따라간 비율 | 케이던스 − BPM (중앙값) |
| --- | --- | --- | --- |
| 130 이하 | 4 | 100% | −0.9 |
| 130~150 | 12 | 17% | +10.5 |
| 150~170 | 178 | 86% | +0.4 |
| 전체 | 194 | 82% | 1.6 (절댓값) |

BPM으로 페이스 예측(초/km, 159구간)과 참고용 속도 → 케이던스(spm, 194구간):

| 방법 | 페이스 MAE | 페이스 치우침 | 케이던스 MAE |
| --- | --- | --- | --- |
| population | 53.8 | +37.4 | 3.98 |
| bayes_cued_all | 36.8 | +7.2 | 3.85 |
| **bayes_cued_followed** | **33.1** | **−0.7** | **3.66** |

러닝별 페이스 MAE(population → bayes_cued_followed): 10/20 48.8 → 69.9, 10/22 71.9 → 32.5, 10/28 45.2 → 18.7, 11/02 56.3 → 19.1. 10/28 두 번째 러닝은 BPM을 따라간 구간이 없어 채점하지 않았다.

### 해석

1. **큐를 켠 기록도 BPM을 따라간 구간만 쓰면 보정에 쓸 수 있다.** 페이스 치우침이 +37.4 → −0.7초/km로 거의 사라져 그 사람의 경향을 잡는다.
2. **따라가지 않은 구간은 빼야 한다.** 큐 켠 구간 전부를 쓰면 36.8로 조금 덜 좋고, 다른 사람 기록(10/27)이 섞였을 때는 69.0까지 나빠졌다(따라간 구간만이면 46.8). 필터가 안전장치 역할을 한다.
3. **평소 케이던스보다 크게 낮은 BPM은 잘 따르지 않는다**(130~150에서 17%). 너무 낮은 BPM을 주면 사용자가 못 맞출 가능성이 크다.
4. **BPM만으로 페이스가 정확히 정해지지는 않는다.** 같은 BPM 160을 따라 뛴 구간도 2.42~3.17 m/s(6:53~5:15/km)로 퍼진다. 케이던스가 같아도 보폭이 바뀌기 때문이다. 10/20처럼 그날 같은 BPM에서 더 느리게 뛰면 보정이 오히려 나빠진다.
5. **Zenodo 강제 케이던스 데이터는 쓰지 않았다.** 트레드밀에서 메트로놈 150~190을 준 조건인데, stride 시간으로 구하면 요청한 변화의 약 14%만 따라간 것으로 나오고, 같은 시간의 stride 개수는 목표에 비례해 늘어(150 → 190에서 55 → 68개) 두 결과가 맞지 않는다. 데이터 구성을 확인하기 전에는 판단하지 않는다.

### 서비스 규칙 그대로 사람별 채점 (BPM-008·009, `evaluate_service.py`)

`target_bpm.py`를 그대로 불러 실제 서비스처럼 채점했다. 서비스는 사용자마다 그 사람의 지난 기록만 쓰므로 **사람마다 따로** 채점하고, 각 러닝은 그 사람의 앞선 러닝만 쓴다(미래 기록 미사용). 위 평가(러닝 하나씩 빼기)는 뒤 러닝도 보정에 썼다.

| 사람 | 기록 | 채점 |
| --- | --- | --- |
| P1 (11절 개인 기록) | 큐 없이 뛴 러닝 93회, 60초 구간 | A |
| P2 (위 워치 데모 앱 기록) | 큐 켠 러닝 6회. BPM-009에서 6번째 러닝(24.8분, BPM 159~163, 20초 구간 67개 중 97%가 BPM을 따라감)을 더했다. 4번째 러닝은 BPM을 따라간 구간이 없어 빠진다 | C |
| P3 (BPM-009 새 사용자) | 큐 켠 러닝 1회(34분, BPM 155~165). BPM을 따라간 비율은 155에서 94%, 160·165에서 50%·14% | C |

- A. 큐 없는 러닝: 그 구간 실제 페이스를 목표로 서비스가 줄 BPM과 실제 케이던스(각 러닝 첫 구간은 첫 1분 보정용이라 제외).
- C. 큐 켠 러닝마다 첫 1분(BPM을 따라간 20초 구간 3개)은 보정에만 쓰고, 나머지 BPM을 따라간 구간에서 "이 BPM이면 몇 초/km"를 채점한다. 그 러닝의 실제 페이스 중앙값 하나로 맞혔을 때(`oracle_run_median`)도 참고로 낸다(BPM이 여러 개인 러닝에서는 하한이 아니다).

A. P1 케이던스(spm, 1,426구간):

| 방법 | MAE | 치우침 | ±5 안 |
| --- | --- | --- | --- |
| 평균 직선 | 5.67 | −5.28 | 48% |
| 처음 사용자 흐름(평균 직선 + 첫 1분 보정) | 3.37 | −1.76 | 77% |
| **기록 있는 사용자(최근 20회 보정, 서비스)** | **2.79** | +0.46 | **86%** |

C. BPM으로 페이스 예측(초/km, 괄호는 치우침·±30초 안 비율):

| 방법 | P2, 지난 기록 있는 러닝 4회 (175구간) | P2 6번째 러닝 (62구간) | P3 (78구간) |
| --- | --- | --- | --- |
| 평균 직선 | 51.6 (+49.7, 18%) | 41.8 (+36.3, 42%) | **16.4 (+16.4, 97%)** |
| **그 사람 지난 기록 보정(서비스)** | **27.2 (+17.0, 57%)** | **29.5 (+2.0, 45%)** | 기록 없음 |
| 첫 1분만 보정 | 40.7 (+20.7, 33%) | 37.8 (−16.5, 34%) | 20.6 (+20.6, 94%) |
| 지난 기록 + 첫 1분 | 27.6 (+13.9, 56%) | 30.5 (−7.4, 44%) | 기록 없음 |
| (참고) 러닝 페이스 중앙값을 미리 앎 | 22.0 | 21.7 | 4.6 |

P2 러닝별 평균 직선 → 지난 기록: 2번째 75.4 → 46.3, 3번째 46.8 → 20.5, 5번째 57.6 → 20.2, 6번째 41.8 → 29.5. 첫 러닝은 기록이 없어 평균 직선 52.5, 첫 1분 보정 56.4였다. P3 케이던스(속도 → 케이던스)는 평균 직선 3.13 spm(±5 안 97%), 첫 1분 보정 3.58 spm(88%)이었다.

해석:

1. **케이던스는 서비스 규칙대로 잘 맞는다.** P1은 기록이 있으면 2.79 spm, 86%가 ±5 안이다. 처음 사용자 흐름도 평균 직선보다 크게 낫다(5.67 → 3.37).
2. **큐를 켜고 뛰는 사람도 자기 지난 기록으로 보정하면 BPM → 페이스가 크게 좋아진다.** P2는 51.6 → 27.2초/km, ±30초 안 18 → 57%다. 그 러닝 페이스 중앙값을 미리 알아도 22초가 남으므로 거의 그 수준이다. 지난 러닝이 2회 이상 쌓인 뒤부터 20초대였다.
3. **러닝 안 흔들림이 크다.** P2 6번째 러닝에서 BPM 159일 때 약 5:26/km, 161~163일 때 약 6:10/km로 같은 케이던스에서 페이스가 크게 달랐다.
4. **첫 1분 보정은 도움이 되지 않았다.** P2에서 첫 1분만 쓰면 40.7로 지난 기록(27.2)보다 나쁘고, 지난 기록에 더해도 27.6으로 같다. P3는 16.4 → 20.6으로 오히려 나빠졌다. 기록이 있으면 첫 1분을 쓰지 않는 지금 규칙이 맞고, 처음 사용자 첫 1분 보정은 사람이 더 모이면 다시 확인한다.
5. **평균 직선은 큐 켠 두 사람 모두 느리게 예측했다**(+16 ~ +50초/km). 같은 BPM에서 실제로는 보폭이 길어 더 빨리 뛰었다. 평균 직선이 트레드밀 데이터로 만들어졌고, 실외에서 보폭이 더 긴 것과 맞는다(10절). 기록이 없는 사용자의 처음 BPM이 이만큼 틀릴 수 있다.
6. **서비스 규칙은 바꾸지 않는다.** 조건마다 1명씩이고 새 사용자는 러닝 1회뿐이다. 실외 기록이 쌓이면 평균 직선을 실외 기록으로 다시 맞춘다.

## 13. 서비스 적용 흐름

8·10·11·12절 결과로 정한 흐름이다. 최근 20회, ±5 spm, 3 spm은 잠정값이다.

| 사용자 | 러닝 시작 | 러닝 중 | 러닝 후 |
| --- | --- | --- | --- |
| 처음 사용자 (보정에 쓸 기록 0개) | 키 prior(키가 없으면 평균 직선)로 BPM | 목표 페이스가 바뀌면 BPM 재계산. 페이스가 일정하고 BPM을 따라간 첫 1분으로 한 번 보정해 3 spm 이상 차이 나면 BPM 변경 | 일정 페이스 구간 저장 |
| 기록이 있는 사용자 | `select_records`로 고른 최근 20회 기록으로 보정한 BPM | 목표 페이스가 바뀔 때만 BPM 재계산 | 일정 페이스 구간 저장 |

- 첫 러닝에서 쓸 구간이 하나도 남지 않았으면(너무 짧거나 BPM을 전혀 따라가지 않음) 다음 러닝도 처음 사용자로 본다.
- 기록이 있는 사용자가 평소와 다르게 뛴 날(피로·오르막 등)은 그 러닝 안에서 바로잡지 않는다. 11절 기준 84회 중 1회였고, 그날 기록은 다음 러닝부터 반영된다.
- 서버에는 구간마다 큐를 켰는지와 그때의 목표 BPM을 함께 저장해야 한다. 그래야 BPM을 따라간 구간을 고를 수 있다.

## 15. 한계

- **실제 워치 데이터가 적다:** 개인 기록(11절)과 큐 켠 기록(12절)이 서로 다른 사람 각 1명이고, 새 사용자 확인(BPM-009)도 1명 1회다. 여러 사람의 서비스 기록으로 다시 확인해야 한다. 워치의 GPS 속도와 손목 케이던스는 연구용 측정보다 흔들리므로 σ²도 다시 추정해야 한다.
- **느린 속도:** 2 m/s(8:20/km)보다 느린 데이터가 없다. 그보다 느리면 직선을 연장하게 되므로 BPM을 60~220과 사용자 편한 범위로 제한한다.
- **성별·수준 편향:** Fukuchi는 거의 남성(35/36)이고 경기 수준 러너다. 여성·키 작은 사용자·초보에 대한 키 효과와 보폭은 확인하지 못했다.
- **경사:** 개인 기록(1명, 대부분 평지)에서는 경사 항 효과가 없어 넣지 않았다(11절 BPM-007). 언덕이 많은 사용자에게는 다를 수 있다.
- **트레드밀 prior:** prior는 트레드밀 기록으로만 학습했다. 실외(5명)에서는 기록 없이 11.8 spm으로 트레드밀 평가보다 크게 틀렸다(10절). 실외 기록이 쌓이면 실외용 prior로 다시 학습해야 한다.
- **BPM으로 페이스를 정확히 정하지는 못한다:** 같은 BPM에서도 날마다, 한 러닝 안에서도 보폭이 달라 페이스 오차가 약 30초/km 남는다. 큐 켠 사람도 자기 기록으로 보정하면 약 27초/km이고, 그 러닝 평균 페이스를 알아도 약 22초가 남는다(12절 BPM-008·009).
- **잠정 기준값:** 최근 20회, BPM을 따라간 기준 ±5 spm, 첫 1분 보정 기준 3 spm은 1명 데이터로 정한 값이다.
- **서비스 연결:** 구간 길이(개인 기록 60초, 큐 켠 기록 20초)를 서비스에서 어떻게 맞출지, 사용자 보정값을 어디에 저장할지, 키를 서버에서 받을 수 있는지는 백엔드와 정해야 한다.
