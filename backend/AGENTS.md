# Backend AGENTS.md

루트 [AGENTS.md](../AGENTS.md)의 공통 규칙을 전제로, 백엔드 기능 구현·수정과 실행 환경 구성에 적용한다.
프론트엔드·워치·AI·인프라에는 이 절차와 템플릿을 자동 적용하지 않는다.
아래 코드 경로는 저장소 루트 기준이다.

개발 전 지침·양식·작업 절차 등 준비 문서만 정비하는 작업은 별도 플랜·리뷰 파일을 만들지 않고,
관련 문서 간 정합성·경로·링크를 검토한 결과를 대화에 남긴다. 디렉터리 위치나 Jira의 `[BE]`
접두어만으로 백엔드 구현 절차를 적용하지 않는다. 실제 API·스키마 계약, 코드 또는 실행 설정을
변경하는 작업은 문서 정비 예외에 포함하지 않고 아래 영향 기준으로 분류한다.

## 1. 기준 문서

- 요구사항: `docs/design/requirements.md`, `docs/design/mvp.md`
- API 계약: `docs/design/api/`, 논리 스키마: `docs/design/db/erd.md`, 물리 스키마: `docs/design/db/schema.sql`
  - 구현은 계약을 따른다. 계약과 다르게 구현해야 하면 임의로 진행하지 않고
    합의 후 문서를 먼저 수정한다. API 초안을 확정 계약으로 취급하지 않는다.
  - 명세에 없는 API, Entity, 필드를 임의로 추가하지 않는다.
- 코드 규칙: [백엔드 코드 컨벤션](../docs/development/backend-convention.md)
  - 문서의 상태를 확인한다. 특정 기술의 작성법이 있다는 이유만으로 해당 기술이 도입·설정됐다고 가정하지 않는다.
  - 담당 도메인·공통 코드 소유권은 [역할 분담 문서](../docs/development/backend-role-assignment.md)와
    현재 Jira·팀 합의를 확인한다. 역할 문서는 작성 틀만 준비된 상태이며 미정 항목을 임의 배정하지 않는다.
  - 컨벤션 예외는 구현 전에 이유와 대안을 제시한다. 다른 담당자 소유 도메인과 공통 설정을 임의로 수정하지 않는다.
- 아키텍처 결정: `docs/adr/`
- 실행·빌드 명령은 [백엔드 README](README.md)를 따른다.

## 2. 검증

현재 백엔드는 Java 21·Spring MVC, Gradle(`build.gradle`), Spring Data JPA, Flyway를 사용하기로 결정했다.
코드 작성 도구와 방식은 컨벤션에 따라 Spotless·AOSP, Lombok, record DTO, Bean Validation을 사용한다.
설정 버전·준비 사항은 `backend/README.md`를 따른다. `backend`에서 완료 검증으로
`./gradlew clean build`를 실행한다. Windows PowerShell에서는 `.\gradlew.bat clean build`를 쓴다.
빌드는 읽기 전용 `spotlessCheck`와 DB 통합 테스트를 포함한 전체 테스트를 실행한다.
포맷 수정은 `spotlessApply`로 별도 수행한다. Docker Linux 엔진이 필요하며 실행하지 못한
DB 테스트를 건너뛰어 완료 처리하지 않는다. IntelliJ 실행·운영 배포 검증과 빌드 결과는 구분한다.

작은 코드 변경도 관련 테스트 통과는 필수다. 문서 등 실행 코드가 없는 변경은 링크·내용 정합성 등
사전에 정한 대체 검증을 수행한다. 테스트 코드만 바꾸어도 해당 테스트를 실행한다.
필수 검증을 영향도 판단으로 임의 제외하거나 기대값을 약화해 통과시키지 않는다.
완료 검증에서 작업 범위 밖의 파일을 수정하지 않는다.

결과는 통과·실패·미실행·해당 없음으로 구분하고 명령·대상 상태·근거를 남긴다.
필수 검증의 실패·미실행은 완료가 아니다. 환경 부족은 미실행으로 보고한다.
검증 후 코드를 바꾸면 영향받는 검증을 다시 실행한다.

## 3. 적용 범위

먼저 트리거로 위험을 판단하고, 트리거가 없는 작업은 변경 내용과 복잡도로 분류한다.
파일 수나 수정 줄 수만으로 판단하지 않는다. 섞이면 가장 높은 단계를 따른다.
판정과 근거는 플랜 파일 첫머리에, 파일을 생략하면 대화에 적는다.
문서·테스트 변경이어도 계약이나 검증하려는 동작이 트리거에 해당하면 게이트를 우선한다.

| 단계 | 조건 | 적용 |
| --- | --- | --- |
| 검증만 | 트리거 없는 문서·주석·테스트 코드만 변경 | 대화에 범위·검증 기준 기록, 자체 점검과 2장 검증. 플랜·리뷰 파일 및 독립 리뷰 생략 가능 |
| 기본 / 작은 변경 | 요구와 수정 위치가 명확하고 영향이 국소적이며 트리거 없음 | 대화에 짧은 계획, 관련 테스트·자체 점검. 플랜·리뷰 파일 및 독립 리뷰 생략 가능 |
| 기본 / 일반 기능 | 트리거가 없고 작은 변경 조건을 충족하지 않음 | 플랜 파일, 구현과 분리된 독립 리뷰 1회와 리뷰 파일 |
| 게이트 / 높은 위험 | 아래 트리거 중 하나 이상 | 플랜 파일과 사람 승인, 구현 및 서로와 분리된 A/B 리뷰와 통합 파일 |

짧은 계획에도 작업 목적·범위와 제외 범위, 변경 대상, 보호할 기존 변경, 완료 조건과
검증 방법을 적는다. 파일 생략이 테스트·검증 생략을 뜻하지 않는다.
진행 중 영향이 커지면 재분류하고 대화의 계획·검증 기록을 플랜 파일로 옮긴다.
게이트로 바뀌면 해당 구현을 계속하기 전에 변경된 플랜에 사람 승인을 받는다.

트리거. diff 또는 플랜에 하나라도 있으면 해당한다.

- `docs/design/api/`, `docs/design/db/erd.md`, `docs/design/db/schema.sql` 변경 또는 그 계약과 다른 구현
- DB 마이그레이션, 공통 모듈·보안 설정, 다른 담당자 소유 도메인
- `@Transactional` 경계의 신설·변경, 한 유스케이스에서 둘 이상의 Repository 쓰기
- 인증·인가 코드, 토큰·쿠키, 건강·GPS 개인정보 접근
- 러닝 기록 유실·중복, 동시성, 업로드 재시도·순서 보장에 영향을 주는 변경
- 메시지 발행·소비와 캐시 키·TTL(해당 기술이 도입된 경우)
- 빌드·의존성·실행·배포 설정, `.env.example`

트리거는 파일명·키워드 존재만이 아니라 실제 변경 내용과 영향으로 판단한다.
계약·동작·설정값·적용 범위가 그대로인 오탈자·주석·설명·서식 수정은 근거를 적고
게이트에서 제외할 수 있다. 영향이 불명확하면 관련 계약과 사용처를 확인해 판정한다.
계약과 다른 구현은 게이트 승인만으로 허용되지 않는다. 1장의 합의·문서 수정 원칙을 먼저 따른다.

## 4. 작업 절차와 게이트

기본·게이트 단계에서 AI는 계획, 구현, 리뷰의 완료 기준을 충족한다.
파일과 독립 리뷰의 생략 여부는 3장을 따른다. 산출물은 다음
단계가 Jira 요구사항, 정본 문서, 저장소 상태와 함께 작업을 재현할 수 있을 정도로 작성한다.
동일 worktree를 여러 작업자가 동시에 수정하지 않는다.
작업 재개·인계 시 브랜치·기준 커밋·diff·플랜·검증 상태를 다시 확인한다.

1. **계획(플랜)** — 파일이 필요한 작업은 루트 `plans/<Jira-Key>.md`에 작성한다(5장).
   첫 설명은 **어떤 작업을 하는가**로 시작한다. 초기 구성·신규 구현·수정을 모두 다루며,
   작업 목적·완료 후 가능한 동작, 범위와 제외 범위, 구현 방향과 선택 이유를 먼저 설명한다.
   변경 작업에만 필요한 현재 문제와 변경 전후를 적는다. 짧은 예시·흐름도·의사코드는
   이해에 필요할 때 사용하되 구현 코드를 중복 작성하지 않는다.

   - **완료 조건은 표가 기본**이다. AC ID, 사람이 읽는 완료 조건, 준비 상황·입력,
     확인할 행동, 정확한 기대 결과, 확인 방법을 적는다. 복잡한 항목에만 상세 설명을 붙인다.
     응답·오류 코드·필드·DB 상태 변화 등 판정에 필요한 값은 유지한다.
     설명 없는 내부 용어와 “정확하게”, “정상 동작”만으로 통과 기준을 대신하지 않는다.
   - 각 AC를 근거 문서 절과 테스트(이름·전제·입력·기대 결과) 또는 대체 검증에 연결한다.
     한 AC에 여러 테스트를 연결할 수 있으며 정상·경계·실패·재시도·권한·동시성 중
     관련 사례를 포함한다. 테스트 이름과 실행 명령 등 추적 정보는 뒤에 배치한다.
   - 자동 테스트, 공통 완료 검증, 추가 검토, 미실행·대체 확인을 구분한다.
     자동화할 수 있는 검증을 문서 구성 편의 때문에 대체 검증으로 낮추지 않는다.
   - 미확정 사항은 확정된 기준·제안과 구분하고, 이유·선택지·영향받는 AC·결정 시점을 적는다.
     미확정 정책을 기대 결과에 확정처럼 쓰지 않는다. 그 결정에 의존하는 구현은 보류한다.
   - 3장 판정·트리거, 조건부 리뷰 관점, 공통 파일 영향·합의 상태, 브랜치·기준 커밋과
     기준선(시작 시점의 미커밋 변경 목록)을 남긴다. 이후 단계는 기존 변경을 보호한다.

   완료 기준: 모든 동작에 테스트 또는 대체 검증과 통과 조건이 대응하고, 착수 범위의
   미확정 사항이 해소되며 계약·스키마·공용 파일 영향이 합의되어 있다.
2. **구현** — 완료 기준: 계획의 인수 테스트가 모두 존재하고 통과하며 2장의 필수 완료 검증이
   성공한다. 테스트 추가·삭제·기대값 변경과 계획 이탈은 사람 확인 후 계획에 기록한다.
   이미 확인받은 내용을 반복 승인받지 않는다. 파일 생략 작업은 대화에 기록한다.
   테스트 실패를 숨기거나 검증 범위를 임의로 약화하지 않는다.
3. **리뷰** — 변경 단위는 관련 파일을 포함한 하나의 동작 또는 책임으로 묶는다.
   해당 단위의 diff와 관련 계약 절을 읽고 필요한 관점을 같은 검토 과정에서 적용한다.
   관점마다 동일 자료를 처음부터 반복해서 읽지 않되, 판단에 필요한 호출부·기존 구현·계약은
   추가 확인한다. 각 리뷰 세션에서 Secret은 전체 diff를 점검하고, 단위 간 계약·트랜잭션
   경계·오류 코드 정합성은 마지막에 종합 확인한다. 실제 인증정보 파일은 읽지 않는다.
   수정이나 새 영향이 발견되면 필요한 부분을 다시 검토한다.

   - 계약 정합성 · 정확성(경계 조건, 실패 경로) · 보안(입력 검증, Secret)
   - 테스트 실효성: AC와 실제 테스트의 대응, 검증 내용, 기대값 변경 기록의 타당성
   - 조건부 관점은 아래 표와 변경 영향에 따라 각각 적용 여부·근거를 기록한다.
     작업을 승인·독립 리뷰 대상으로 올리는 **게이트**와 **조건부 리뷰 관점**을 구분한다.
     읽기 전용이어도 트랜잭션 경계 신설·변경은 검토하며, 여러 조회 사이의 데이터 변화가
     결과에 영향을 주는지도 판단한다. 쓰기가 없다는 이유만으로 동시성 검토를 제외하지 않는다.

리뷰 편성 및 산출물은 다음과 같다.

- **검증만·작은 변경**: 계획·실제 변경·검증 결과를 자체 점검한다. 파일과 독립 리뷰는
  3장에 따라 생략할 수 있다. 생략 근거를 기록한다.
- **일반 기능**: 구현과 분리된 리뷰어 1명이 관련 관점을 검토하고
  `plans/<Jira-Key>-review.md`에 기록한다.
- **높은 위험**: 구현과 분리된 두 세션 A/B가 동일한 플랜·대상 코드 상태·계약·검증 결과로
  독립 검토한다. 구현자의 결론을 정답으로 주입하지 않고 검증 증거와 미확인 사항을 전달한다.

  - A는 계약·정확성·보안·테스트 실효성과 해당 조건부 관점을 검토한다.
  - B는 각 AC의 전제를 깨는 입력·교차 실행·실패 경로를 검토한다. 해당하는 동시성·트랜잭션·인가
    항목은 구체적인 실행 순서 또는 요청 시나리오로 확인한다. 발견한 결함뿐 아니라 시도한 사례,
    증거·한계를 남긴다. 확인 범위에서 결함을 찾지 못한 것을 전체 안전성의 증명으로 쓰지 않는다.
  - 각각 `plans/<Jira-Key>-review-A.md`, `plans/<Jira-Key>-review-B.md`에 기록한다.
    두 결과가 확정되기 전 서로의 리뷰 파일·결과를 읽거나 전달받지 않는다. 리뷰어는 코드를 수정하지 않는다.
  - 두 결과가 끝나면 AI가 합집합을 `plans/<Jira-Key>-review.md`에 모은다. A-n/B-n 번호를 보존하고
    중복 관계, 채택·기각·후속과 근거를 남긴다. 한쪽만 발견한 지적도 검토한다.
    요구사항 해석·수정 범위·위험 수용에 선택이 필요한 항목은 사람이 판단하며 채택 목록만 수정한다.

공통 관점에 더해 관련 변경에만 다음 관점을 적용한다.

| 변경 기능 | 조건부 리뷰 관점 |
| --- | --- |
| 인증·건강/GPS 접근 | 소유자·동의·권한 철회, 우회 요청, 정보 노출 |
| 러닝 상태·저장·업로드 | 중복·순서 역전·동시 실행, 트랜잭션·재시도·복구 |
| 모바일·워치 연동 API | 연결 단절 시 서버 처리, 권한·단위·시간 정합성 |
| 추론·외부 API | 누락·잘못된 입력, 타임아웃·오류 전파, 계약 불일치 |
| 백엔드·공통 설정 | 적용 범위, 기동 실패·복구, 비밀정보 취급 |

- **플랜 승인**: 게이트 단계는 플랜 완료 후 사람이 확인하고 승인·수정 지시를 플랜에 추기한 뒤 구현한다.
  이미 승인된 내용은 반복 확인하지 않는다.
- **분리 리뷰**: 필요한 독립 리뷰는 구현과 다른 세션 또는 사람이 플랜·diff·정본 문서와 검증 결과를 보고 수행한다.
  높은 위험은 위 A/B 독립성 규칙도 따른다. 구현자의 재독을 독립 리뷰로 기록하지 않는다.
  리뷰어는 코드를 수정하지 않는다. 플랜 승인은 사람이 하고, 독립 리뷰·결과 통합은 AI가 수행할 수 있다.
  분리 리뷰 자체를 매번 사람의 승인으로 취급하지 않는다. 사람은 선택이 필요한 항목을 판단한다.
- **리뷰 완료**: 필수 지적은 수정·재테스트 후 해당 부분과 영향 범위를 재검토한다. 일반 기능에도 적용한다.
  필요한 재검토도 구현과 분리해 수행한다. 새 영향이 없으면 전체 A/B 리뷰를 반복하지 않는다.
  새 영향이 있으면 해당 범위에 필요한 A/B 관점을 다시 적용한다.
  필수 결함을 근거 없이 기각하거나 후속으로 돌려 완료 처리하지 않는다.
  필요한 리뷰를 수행하지 못하면 미실행으로 보고한다.
  팀원에게 메시지를 보내는 것은 사용자 요청이 있을 때만 한다.

게이트 단계 MR 5건 연속으로 사후 누락이 0이면 리뷰 기준 완화를, 기본 단계 MR에서 사후 누락이
나오면 트리거 확대를 검토한다. 변경 위험·검토 범위·관찰 여부를 함께 보고 자동 변경하지 않는다.
관찰하지 못한 값은 미확인이며 누락 0건으로 세지 않는다.

## 5. 플랜과 기록

- 플랜과 리뷰 파일은 **저장소 루트의 `plans/`** 에 둔다. 이 문서가 `plans/`로만 적은 곳도
  모두 루트를 가리킨다. `.gitignore`의 무시 규칙이 루트에 고정된 `/plans/`와 하위 디렉터리의
  `/*/plans/`뿐이므로, 그 밖의 위치에 두면 커밋하지 않기로 한 기록이 커밋 대상이 된다.
- worktree에서 작업했으면 완료 후 산출물을 기본 체크아웃의 루트 `plans/`로 옮긴다.
  worktree를 정리하면 그 안에만 있던 플랜과 리뷰 기록이 함께 사라진다.
- 플랜과 리뷰 결과는 커밋하지 않는다. MR 본문에 플랜 요약, 플랜 대비 변경점과
  리뷰 결과 요약을 남긴다.
- 플랜과 리뷰 파일은 [플랜 양식](templates/plan.md)과 [리뷰 양식](templates/review.md)으로
  작성한다. 일반 기능·높은 위험은 작업 설명·범위·완료 조건·검증 연결·분류 근거·기준선·기준 문서를
  필수로 남긴다. 미확정·공통 영향·조건부 관점이 없으면 사유와 함께 없음/해당 없음으로 적는다.
  상세 시나리오·그림은 필요할 때만 추가한다. 승인·실행 결과·변경 기록은 진행에 맞춰 추기하고
  아직 관찰하지 못한 결과를 통과나 0으로 채우지 않는다.
- 리뷰 파일에는 읽은 기준 문서 절 수, 적용한 조건부 관점과 근거, 검토자·세션·모델,
  발견 사항 수, MR 리뷰·병합 후 뒤늦게 발견된 누락을 기록한다. A/B 통합 시 각 수치를 구분하고
  발견 사항은 중복 관계를 반영한다. 측정 칸은 값 또는 미확인 사유로 채운다.
- MR 본문 "테스트" 절에는 AC별 테스트·대체 검증과 결과, 실행 명령·대상 상태·증거,
  리뷰 편성과 통합 결론·필수 지적 처리·측정값, 남은 위험·미실행을 요약한다.
  파일 생략 작업은 대화의 짧은 계획·검증 결과와 생략 근거를 옮긴다. 로컬 파일 경로만 전달하지 않는다.
- 플랜에서 프로젝트 수준 결정이 나오면 `docs/adr/`로 승격한다.
- 미래 작업에 필요한 사실을 플랜이나 MR 본문에만 남기지 않는다. 계약, 스키마와
  코드 규칙 변경은 반드시 정본 문서(`docs/design/api/`, `docs/design/db/erd.md`, `docs/design/db/schema.sql`,
  확정된 백엔드 규칙과 `docs/adr/`)에 반영한다.

- 아직 관찰할 수 없는 측정값은 사유와 함께 미확인으로 적는다. 작은 변경의 리뷰 생략도 MR에 명시한다.
- worktree를 사용하면 해당 Jira의 작업 디렉터리에서 수행한다. 기록 보존 시 기존 동명 파일을 덮어쓰지 않는다.
