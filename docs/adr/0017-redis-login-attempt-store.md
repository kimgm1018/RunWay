# ADR-0017: 로그인 실패 횟수와 잠금 상태도 인증용 Redis에 저장한다

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-10-28 |
| 결정자 | 작업 요청자(193번의 저장소·만료·초기화·복구 권장안 승인) |
| 관련 | [S15P31E105-193](https://ssafy.atlassian.net/browse/S15P31E105-193), [U01 로그인 제한](../design/api/users.md#로그인-연속-실패-제한), [인증 저장소 경계](../design/db/erd.md#인증-저장소-경계), [ADR-0015](0015-redis-refresh-token-store.md) |
| 대체 관계 | —. ADR-0015의 Refresh Token 결정은 유지하고 로그인 실패 상태로 적용 범위를 확장한다. U01의 기존 DB 저장 방침은 이 결정으로 변경한다. |

## 맥락

193번은 아이디별 연속 로그인 실패와 일시 잠금을 구현한다. 기존 U01은 DB 영속 저장을 요구했고 최초 구현 플랜은 PostgreSQL 테이블·행 잠금을 제안했다. 한편 192번 이후 인증용 Redis와 토큰 저장·영속화·장애 처리 구성이 이미 존재한다.

작업 요청자는 실패 상태도 Redis에 저장하는 방안을 제안하고 구현 전에 관련 정책부터 결정하도록 요청했다. 2026-10-28 현재 대화에서 Redis 사용, 마지막 실패 후 24시간 동안 추가 실패가 없는 1~4회 기록의 초기화, 자격증명 확인·Redis 토큰 저장 완료 시 성공 초기화, 운영자 확인 후 빈 저장소 복구 시 실패·잠금 초기화 허용을 함께 승인했다. 시간초과 뒤 쓰기가 이미 반영됐을 수 있으며 자동 재전송하지 않는 설명도 포함됐다.

## 결정

로그인 실패 횟수와 잠금 상태는 기존 인증용 Redis를 기준 저장소로 관리한다. 제출 아이디별 상태를 원자적으로 변경하고 기록·잠금의 만료에 TTL을 활용한다. 사용자·비밀번호 해시는 PostgreSQL에 유지하며 실패 상태를 위한 테이블이나 자동 대체 저장소를 추가하지 않는다.

실패 기록의 수명과 초기화·복구 동작은 [U01의 확정 계약](../design/api/users.md#로그인-연속-실패-제한)을 따른다. 성공 초기화는 클라이언트의 응답 수신과 분리하고 서버의 자격증명 확인·사용 가능한 로그인 계열 저장 완료를 기준으로 한다. 서로 다른 저장소의 공동 커밋·롤백이나 결과 불확실한 쓰기의 미실행을 보장하지 않는다.

기존 인증용 Redis의 영속화·메모리 퇴출 방지·장애 응답 기준을 재사용한다. 정상 재시작에는 상태를 보존하되, 신뢰할 수 있는 상태를 복구할 수 없어 운영자가 빈 저장소로 재개하는 경우 기존 실패·잠금이 사라지는 예외를 수용한다. 일시적 장애 시 자동 초기화하거나 인증을 허용하지 않는다.

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 기존 인증용 Redis 사용 (선택) | 아이디별 원자적 상태 변경과 만료 관리, 실패 쓰기의 PostgreSQL 부하 분리, 기존 운영 구성 재사용 | Redis 내구성·용량과 장애 처리에 의존. DB 종료·응답 유실과 초기화 시점의 차이를 수용해야 함 |
| PostgreSQL 독립 테이블과 행 잠금 | 사용자 상태와 같은 DB에서 실패 상태를 관리하고 트랜잭션 경계를 구성 가능 | 미가입 아이디도 저장할 테이블·마이그레이션·만료 정리가 필요하고 실패 쓰기가 DB 자원을 사용 |

## 결과

- **얻는 것**: 기존 인증 저장소에서 토큰 발급과 실패 제한을 연결하고, PostgreSQL 실패 테이블 없이 만료와 동시 요청을 처리한다. 성능 향상은 기대 효과이며 실측 결과가 아니다.
- **감수하는 것**: 보존 기간이 지난 실패는 누적되지 않으며 복구 불가능한 유실 후 운영자 승인 복구에서는 기존 잠금도 풀린다. 응답 오류가 이미 반영된 초기화·실패 증가를 되돌린다는 보장은 없다. 유한한 보존 기간만으로 메모리 고갈이나 타인 아이디 잠금 공격을 막지 못한다.
- **후속 작업**: 193번에서 Redis 상태 모델·스크립트·토큰 발급 결합을 구현하고 최초 상태 생성, 만료 경계, 성공·실패 경합, 시간초과·부분 쓰기, 정상 재시작과 빈 저장소 복구를 검증한다. 실제 ACL 허용 명령과 메모리 부족 동작도 확인한다. 이 결정의 채택 자체는 실패 제한의 구현·검증 완료를 뜻하지 않는다.
- **재검토 조건**: 실패 기록의 수명·잠금 악용·메모리 사용량 또는 복구 보장이 제품 요구를 충족하지 못하면 보존·접근 제한 정책과 저장소 선택을 다시 검토한다.

## 기술 참고

2026-10-28 Context7 `/redis/docs`로 스크립트 원자적 실행과 쓰기 후 중단의 제약을 조회했다. 저장소 대상은 Redis 8.2.11이며 반환 문서는 버전이 고정되지 않은 최신 문서다. 8.2.11에서의 장애·원자성 검증을 수행한 것으로 해석하지 않는다.

- [Redis Lua 실행](https://redis.io/docs/latest/develop/programmability/eval-intro/): 서버 안의 조건 검사·상태 변경 실행 격리.
- [Redis 스크립트 실행 제약](https://redis.io/docs/latest/develop/programmability/): 쓰기 후 중단과 시간초과의 한계. 클라이언트 시간초과를 상태 미변경의 증거로 사용하지 않는다.
