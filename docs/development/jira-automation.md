# AI Jira 업무 등록 및 개발 연계

자연어 요청을 AI가 업무 초안으로 정리하고, 사람의 확인을 받은 뒤 로컬 Python 스크립트가 Jira Cloud에 등록한다. 스크립트 자체가 자연어를 해석하거나 별도의 AI 서비스를 호출하지 않는다. AI가 `AGENTS.md`를 읽고 조회·제안·실행을 담당한다.

## 개발자별 최초 설정

저장소 최상위 폴더에서 Python 3.11 이상을 확인한다.

```powershell
python --version
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r scripts/jira/requirements.txt
```

기존 가상환경이 있으면 재사용한다. 현재 구현은 Python 표준 라이브러리만 사용하므로 추가 패키지는 없다. PowerShell에서 활성화가 차단되면 실행 정책을 변경하지 않고 `.\.venv\Scripts\python.exe`로 실행할 수 있다.

`.env.example`을 참고해 **본인이** 로컬 `.env`에 값을 입력한다. 기존 `.env`는 덮어쓰지 않고 필요한 항목만 추가한다. 스크립트는 실행 위치와 관계없이 저장소 루트의 `.env`를 읽고, 같은 이름의 환경변수가 있으면 환경변수를 우선한다. 단순 `KEY=VALUE`, 한 줄 따옴표, 주석만 지원하며 변수 확장·명령 실행은 하지 않는다.

| 항목 | 값 |
| --- | --- |
| `JIRA_BASE_URL` | `https://ssafy.atlassian.net` |
| `JIRA_PROJECT_KEY` | `S15P31E105` |
| `JIRA_BOARD_ID` | `16659` |
| `JIRA_EMAIL` | 본인의 Atlassian 이메일 |
| `JIRA_API_TOKEN` | 본인이 발급한 API Token |

사이트 주소에 사용하는 일반 API Token과 scope가 있는 Token은 API 주소가 다르다. scoped token을 쓰면 예시 파일의 `JIRA_API_BASE_URL`도 설정한다. `JIRA_BASE_URL`은 이슈 링크를 위한 사이트 주소로 유지한다. Token의 권한에는 사용하는 프로젝트 조회·생성 및 필요한 Jira Software API 접근이 있어야 한다. [Atlassian Token 안내](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account)를 참고한다.

`.env`, Token, 개인 이메일, `.jira/`의 작업 초안·기록은 Git에 올리지 않는다. 인증정보를 AI에게 전달할 필요는 없다.

모든 AI Agent는 `.env`와 실제 인증정보가 포함된 `.env.*` 파일의 내용을 직접 읽거나 AI 컨텍스트로 가져오지 않는다. 사용자가 요청한 작업을 위해 스크립트·프로그램이 내부적으로 해당 값을 활용하는 것은 허용하며, AI가 이를 위한 스크립트를 작성·실행할 수 있다. 파일 내용이나 인증정보를 AI에게 전달하거나 출력·로그에 노출하지 않고, AI는 연결 상태·누락된 설정 이름·처리 결과만 확인한다. 이메일·Token 입력과 수정은 사용자가 직접 하며, AI가 내용을 참고할 수 있는 설정 파일은 인증정보가 없는 `.env.example` 등 예시 파일뿐이다. 공통 규칙은 `AGENTS.md`에 있고 `CLAUDE.md`가 이를 가져오므로 Claude도 같은 규칙을 적용한다.

```powershell
python scripts/jira/create_issues.py --check
```

인증, 프로젝트·보드·필터 접근, 조회·생성 권한, 생성 가능한 유형을 확인한다. **GET 요청만 보내며 Jira를 변경하지 않는다.** 보드 접근과 프로젝트 권한을 각각 확인하므로 운영자가 보드 필터에 해당 프로젝트가 포함되는지도 확인해야 한다. `--check`는 실제 생성 성공이나 모든 필드·스프린트 편집 권한을 보장하는 테스트는 아니다.

## 평소 사용

> “러닝 기록 조회 기능 만들려고 해. Jira에 등록해줘.”

AI가 범위를 확인하고 유형·제목·완료 조건·SP·우선순위와 선정 이유·담당자·Epic·스프린트 및 중복 후보를 제안한다. 신규 Task/Story/Epic의 기본 담당자는 본인(작업 요청자)이다. 담당자를 지정하지 않으면 현재 Jira 계정을 조회해 작업 요청자를 담당자로 제안한다. 명시적인 담당자 또는 미지정 요청을 우선한다. 신규 Task/Story의 기본 스프린트는 보드의 현재 활성 스프린트이며, 명시적인 스프린트 지정 또는 미지정 요청을 우선한다. Epic에는 스프린트를 지정하지 않는다. 확인한 뒤:

Epic은 기존 항목의 목적과 범위를 먼저 확인해 적절한 항목을 재사용한다. 적절한 Epic이 없으면 AI가 새 Epic의 제목·목적·범위를 제안하고 생성할지 물어본다. 사용자 확인 후 Epic을 생성·검증하고, 그 Epic에 연결할 Task/Story의 최종 내용을 확인받아 생성한다. 이미 구체적인 내용을 승인했다면 같은 확인을 반복하지 않는다.

> “확인했어. 생성해줘.”

AI가 생성하고 Key와 링크를 안내한다. 사용자가 JSON이나 실행 명령어를 작성할 필요는 없다. Jira 유형·제목은 팀의 Jira 사용 가이드를 따르고, SP는 아래 스토리포인트 기준을 따른다.

## 스토리포인트(SP) 기준

SP는 **작업의 크기·복잡도·불확실성·검증 난이도**를 비교하는 값입니다. **1점이 1시간이나 1일을 의미하지는 않습니다.**

AI 에이전트를 사용하는 개발 환경을 기준으로, **AI가 포인트와 이유를 제안하고 사람이 확인합니다.**

| SP | 기준 | 작업 예시 |
| --- | --- | --- |
| **1** | 범위가 작고 방법이 명확한 수정 | DTO 필드 추가, 간단한 입력 검증, 텍스트·설정 변경 |
| **2** | 기존 패턴으로 구현하는 작은 작업 | 단순 CRUD API, Repository 추가, 작은 UI 수정 |
| **3** | 여러 파일 수정과 일반적인 테스트가 필요한 작업 | 화면·API 연동, 일반적인 도메인 기능, 간단한 외부 API 연결 |
| **5** | 새로운 설계나 예외 처리·통합 검증이 중요한 작업 | 인증 흐름 추가, 캐싱 적용, 비동기 처리 |
| **8** | 설계가 복잡하거나 불확실성과 검증 부담이 큰 작업 | 동시성 제어, 트랜잭션 재설계, 복잡한 외부 연동 |
| **13** | 여러 시스템에 영향을 주는 큰 변경 | DB·API·이벤트 구조 변경, 대규모 리팩터링 |
| **21** | 한 업무로 완료하기 어려운 매우 큰 작업 | 신규 서브시스템 구축, 광범위한 아키텍처 변경 |

## 우선순위 제안 및 확인 기준

- AI는 `--catalog`의 `priorities`에서 해당 업무 유형의 `values`(사용 가능한 ID·이름)와 `default`(조회된 기본값 또는 `null`)를 확인한다. 목록은 사이트 전체 목록이 아니라 해당 프로젝트·업무 유형의 생성 화면 메타데이터 `priority.allowedValues`를 사용한다. 유형에 따라 값이 다를 수 있으며, 조회 실패나 빈 목록을 임의의 ID로 대체하지 않는다.
- 사용자가 명시한 우선순위를 먼저 적용한다. 사용 불가능하거나 같은 이름이 여러 개라면 임의로 대체하지 않고 사용할 수 있는 값을 보여주어 확인한다. AI가 만드는 초안에는 조회한 ID를 사용하는 것을 권장한다.
- 별도 지정이 없으면 영향 범위와 기능 중단 정도, 기한·장애 대응의 긴급도, 다른 업무를 막는 선행 의존성을 함께 고려해 우선순위와 이유를 제안한다. 예를 들어 다른 업무를 막는 문제는 그 의존성을 이유로 밝히고, 일정이 급하지 않은 개선은 영향 범위와 시급성을 설명한다. SP가 크다는 이유만으로 우선순위를 높이지 않으며, 사실이 부족하면 추정과 확인할 점을 밝힌다. 사용할 이름과 수준은 조회된 목록을 따른다.
- Task/Story/Epic 신규 초안에는 `priority`와 `priority_reason`을 넣고 다른 필드와 함께 사용자에게 보여주어 확인받는다. 명시적 사용자 지정인 경우에도 그 사실과 확인한 이유를 남긴다. 스크립트는 자연어를 분석하거나 자동 점수를 계산하지 않고 AI가 작성한 초안을 검증·저장한다.
- 기존 초안에서 `priority`를 생략하거나 `null`로 두면 Jira 생성 요청에서 해당 필드를 생략하여 Jira 기본값을 사용한다. `priority_reason`도 생략 또는 `null`이어야 한다. 이전 초안에 필드를 자동 추가하지 않아 기존 승인 해시·생성 기록은 유지되며, 이 경우 기본 우선순위의 일치는 검증하지 않는다. 새 초안은 명시적 값을 제안하는 절차를 따른다. 기존 Jira 업무의 우선순위 일괄 변경은 지원하지 않는다.

## AI 및 유지보수 담당자용 실행 방식

```powershell
# 모두 읽기 전용
python scripts/jira/create_issues.py --catalog
python scripts/jira/create_issues.py --catalog --user-query "팀원 이름"
python scripts/jira/create_issues.py --input .jira/drafts/running-history.json
```

`--catalog`의 `current_user`에는 로컬 인증 계정의 `accountId`, `displayName`, 프로젝트 배정 가능 여부인 `assignable`이 반환된다. 이메일·Token은 반환하지 않는다. 현재 계정 또는 배정 가능 여부를 확인하지 못하면 확인하지 못한 값은 `null`로 반환하고, `current_user.question`에 "누구를 담당자로 설정할까요?"를 담아 AI가 사용자에게 묻게 한다. 담당자 조회 실패만으로 카탈로그 조회를 중단하지 않는다. AI는 신규 Task/Story/Epic의 담당자를 별도로 지정하지 않은 경우 `assignable`이 `true`인지 확인하고 이 계정의 `accountId`를 초안의 `assignee`에 넣는다. 스크립트가 초안의 `null`을 자동으로 본인 계정으로 바꾸지는 않는다. 미리보기·승인 해시·생성 검증은 초안에 명시한 담당자를 기준으로 한다.

`--catalog`의 `default_sprint`는 `active,future` 스프린트 목록에서 신규 Task/Story의 기본 스프린트를 판단한 결과다. 스크립트는 판단 결과만 반환하고 초안의 `sprint_id`를 자동으로 채우거나 Jira를 변경하지 않는다.

| 상황 | `default_sprint` | AI 처리 |
| --- | --- | --- |
| 활성 스프린트 1개 | `reason: "active"`, `sprint`에 ID·이름·기간, `question: null` | 종료일과 관계없이 `sprint.id`를 초안 `sprint_id`에 넣어 제안한다. |
| 활성 스프린트 없음 | `reason: "no_active"`, `sprint: null`, `next_sprint`(가장 먼저 시작하는 예정 스프린트 또는 `null`), `question` | 예정 스프린트 또는 미지정 중 사용자가 고르게 한다. |
| 활성 스프린트 여러 개 | `reason: "multiple_active"`, `candidates`, `question` | 후보를 보여주고 사용자가 고르게 한다. |

사용자가 스프린트를 지정하거나 미지정을 요청하면 그 값을 우선한다. `question`이 있으면 답변을 받을 때까지 스프린트를 임의로 정하지 않는다. 미리보기의 `sprint`에는 선택한 스프린트의 ID·이름·상태·기간을 표시하며(미지정이면 `null`), 이를 다른 필드와 함께 보여주어 확인받는다. `sprint_id`는 승인 해시에 포함되므로 스프린트를 바꾸면 미리보기와 승인을 다시 받는다.

연결된 Jira 도구의 계정은 로컬 스크립트 인증 계정과 별개다. 계정이 서로 다르거나 작업 요청자를 식별할 수 없거나 배정할 수 없으면 담당자 조회 실패를 오류로 종료하지 않고 AI가 "누구를 담당자로 설정할까요?"라고 묻는다. 사용자가 답할 때까지 이슈 생성·배정을 보류하고, 답변으로 지정한 사용자의 배정 가능 여부를 조회한다. 계정 ID를 하드코딩하거나 Git 작성자·운영체제 사용자 이름으로 추정하지 않는다.

미리보기는 생성 화면 메타데이터로 유형·Story Points·우선순위·필수 필드를 검사한다. 우선순위가 지정되면 미리보기의 `priority`에 조회한 ID·이름·선정 이유를 표시하고 `fields.priority.id`에 저장할 ID를 넣는다. 우선순위 필드가 없거나 목록에 없는 값·중복된 이름은 생성 전에 차단한다. Epic이 같은 프로젝트의 Epic인지, 담당자가 배정 가능한지, 스프린트가 지정 보드의 활성/예정 스프린트인지도 확인한다. 모든 프로젝트 이슈의 제목을 페이지 끝까지 조회해 `project_issues`로 반환하므로 AI가 의미상 중복을 검토한다. 같은 제목의 정확한 중복은 `exact_duplicates`에 표시한다. 제목만으로 업무 의미를 완벽하게 판단하지 못한다.

초안 JSON은 AI가 다음 형식으로 작성한다. `description`은 일반 텍스트이며 Markdown 문법 변환은 하지 않는다. 완료 조건은 Jira의 글머리 목록으로 저장한다.

```json
{
  "issue_type": "Task",
  "summary": "[Jira] AI 업무 생성 및 개발 연계 자동화 코드 구현",
  "description": "팀 가이드를 실제로 실행할 수 있도록 연동 코드를 구현한다.",
  "acceptance_criteria": ["연결 확인은 Jira를 변경하지 않는다", "승인된 초안으로 이슈를 생성하고 검증한다"],
  "story_points": 5,
  "priority": "High",
  "priority_reason": "후속 업무 등록에 필요한 선행 작업이며 팀 사용 전 검증이 필요하다.",
  "assignee": null,
  "epic": "S15P31E105-21",
  "sprint_id": null,
  "labels": []
}
```

- 로컬 스크립트 유형: `Task`/`작업`, `Story`/`스토리`, `Epic`/`에픽`. Subtask는 생성하지 않는다. 기존 Epic 중 적절한 항목이 없으면 AI가 사용자 확인 후 로컬 스크립트로 새 Epic을 생성하고, 생성된 Key를 Task/Story 초안에 반영한다.
- SP: Task/Story는 위 스토리포인트 기준에 따라 AI가 포인트와 이유를 제안하고 사람이 확인하며, 프로젝트 생성 화면에 Story Points 필드가 있어야 한다. 후보가 여러 개면 `.env`의 `JIRA_STORY_POINTS_FIELD`로 지정한다. ID는 사이트별로 확인한다. Epic은 SP를 생략하거나 `null`로 지정한다.
- 우선순위: `priority`는 조회한 ID 또는 정확한 이름 문자열이다. 지정하면 공백만이 아닌 `priority_reason` 문자열도 필요하다. 위의 `High`는 형식 예시이며 실제 초안은 `--catalog`에서 확인한 해당 유형의 값으로 작성한다. 값과 이유 모두 승인 해시에 포함되며, 이유는 미리보기에 표시하고 Jira 설명이나 별도 필드에 자동 추가하지 않는다.
- 담당자: 조회 결과의 `accountId` 또는 `null`. 신규 Task/Story/Epic은 기본적으로 본인을 담당자로 설정하며, 별도 지정이 없으면 위 절차로 식별한 작업 요청자의 `accountId`를 넣는다. 이메일을 ID 대신 넣지 않는다. 명시적으로 미지정을 요청하면 `null`로 프로젝트 기본 담당자 자동 배정을 막는다. 초안 예시의 `null`은 미지정을 의도한 값이다.
- Epic: Task/Story를 연결할 같은 프로젝트 Epic Key 또는 `null`. 생성 화면의 `parent`를 우선하고 구형 Epic Link 필드도 지원한다. 새 Epic을 생성할 때는 이 항목을 생략하거나 `null`로 지정한다.
- 스프린트: Task/Story는 보드의 활성/예정 스프린트 숫자 ID 또는 `null`(스프린트 지정하지 않음). 별도 지정이 없으면 위 `default_sprint` 절차로 확인한 현재 활성 스프린트 ID를 넣는다. 초안 예시의 `null`은 미지정을 요청한 경우의 형식 예시다. Epic은 생략하거나 `null`로 지정한다.
- Epic 이름: 생성 화면에 별도 Epic Name 필드가 있으면 기본적으로 제목을 저장한다. `epic_name`으로 별도 이름을 지정할 수 있고, 이 값도 승인 해시와 생성 후 검증에 포함된다. Task/Story에는 `epic_name`을 지정하지 않는다.
- 추가 필수 필드가 있는 프로젝트는 생성을 중단한다. 임의 기본값을 넣지 않고 해당 필드를 지원하도록 별도 확장한다.

새 Epic 초안 예시:

```json
{
  "issue_type": "Epic",
  "summary": "[BE] 러닝 기록 관리",
  "description": "러닝 기록 저장·조회·분석 기능을 묶어서 관리한다.",
  "acceptance_criteria": ["관련 Task/Story가 완료되어 러닝 기록 관리 기능을 사용할 수 있다"],
  "priority": "High",
  "priority_reason": "여러 후속 구현 업무가 의존하는 선행 범위를 관리한다.",
  "assignee": null,
  "labels": []
}
```

Epic도 같은 `--input` 미리보기 및 `--apply --approved-sha256` 명령을 사용한다. 생성된 Epic Key를 확인한 다음 Task/Story의 `epic`에 넣고 다시 미리보기한다. Epic과 Task/Story를 일괄로 생성하지 않으므로, Epic 생성만 성공하고 후속 업무 생성이 실패하면 기존 Epic을 재사용한다.

사용자 확인 후 AI는 **해당 미리보기**의 `approval_sha256`를 넘긴다.

```powershell
python scripts/jira/create_issues.py --input .jira/drafts/running-history.json --apply --approved-sha256 <미리보기의_SHA256>
```

기본 실행은 조회이며 `--apply` 없이는 생성하지 않는다. 우선순위와 선정 이유를 포함한 초안·사이트·프로젝트·보드가 바뀌면 해시가 바뀌어 실행이 차단된다. 값이나 이유를 변경했다면 미리보기를 다시 제시하고 사용자 확인을 받는다. 해시는 변경 감지 수단으로, AI는 사람의 실제 확인도 받아야 한다. 동일 제목의 별개 업무를 사람이 확인한 경우에만 `--allow-duplicates`를 추가한다.

생성 후 제목·본문·유형·SP·담당자·Epic·요청한 우선순위와 라벨을 다시 조회해 비교한다. 우선순위는 이름이 아닌 ID로 비교하며, 생성 기록의 `fields.priority`에도 저장하여 `--verify`에서도 검증한다. 불일치하면 `verified: false`, `mismatches: ["priority"]`와 종료 코드 `2`로 보고하며 다시 생성하지 않는다. 스프린트가 지정됐으면 생성 후 스프린트에 배정하고 배정 결과도 확인한다. 생성·스프린트 배정·검증은 하나의 트랜잭션이 아니므로 부분 성공이 가능하다.

## 실패 및 중복 생성 복구

HTTP 오류는 상태와 점검 항목만 출력하며 서버 응답 본문·Authorization·Token은 출력하지 않는다. 요청은 자동 재시도하지 않는다. 인증을 포함한 요청의 리다이렉트도 허용하지 않는다.

생성 전 `.jira/receipts/`에 해시별 기록을 배타적으로 만든다. 같은 PC의 같은 초안 재실행과 동시 실행은 이 기록으로 방지한다. 다른 PC에서 동시에 생성하는 경쟁 조건까지 보장하지는 않으므로 AI의 Jira 중복 확인도 필요하다.

- Key가 반환됐지만 스프린트 지정이나 검증이 실패하면 **이미 생성된 업무**다. 다시 생성하지 않는다. Key·링크를 알려주고 해당 이슈의 실패 항목만 수정한다.
- 읽기 검증은 `python scripts/jira/create_issues.py --verify S15P31E105-123`으로 재실행한다. 이 PC에 저장된 생성 기록이 필요하다. 이 명령은 수정하지 않는다.
- 생성 요청 타임아웃 또는 Key 저장 실패는 결과가 불확실하다. 같은 초안의 재생성을 차단한다. Jira에서 제목·본문·생성 시각·담당자 등을 확인한다. 초안을 수정해 차단을 우회하지 않는다.
- 관리자가 Jira에서 해당 이슈를 찾았다면 로컬 기록의 `key`에 실제 Jira Key를 넣고 `--verify`로 검증한다. `fields`와 `sprint_id`는 변경하지 않는다.
- **미생성을 확인한 경우에만** 관리자가 해당 기록 하나를 삭제하고 승인된 초안을 재실행한다. 기록을 일괄 삭제하지 않는다.
- `.jira` 기록을 유지한다. 검증이 실패하면 성공으로 보고하지 않는다.

종료 코드: `0` 조회/검증 성공, `1` 입력·연결·실행 오류, `2` 이슈는 존재하지만 검증 미완료 또는 불일치.

## 개발까지 이어서 요청

> “생성된 Jira 업무를 구현하고 검증해줘. 커밋·Push·MR 생성은 하지 말아줘.”

또는:

> “구현과 검증이 끝나면 팀 규칙에 맞춰 커밋·Push하고 MR도 생성해줘.”

AI는 최신 `dev` 기준으로 Jira Task/Story마다 별도 worktree와 `<type>/<JIRA-KEY>-<description>` 브랜치를 만들어 요청 범위까지만 진행한다. 같은 업무를 재개할 때는 해당 worktree와 브랜치를 재사용한다. 서로 다른 Jira 업무를 같은 worktree에서 개발하거나 기본 체크아웃에서 브랜치만 전환해 작업하지 않는다. MR 제목에는 Jira Key, 작업 MR 본문에는 `Closes <JIRA-KEY>`를 넣는다.

작업 시작·재개 및 편집·테스트·커밋·Push·MR 실행 전에는 Jira Key, 절대 worktree 경로, 현재 브랜치, 변경 파일 범위를 확인하고 해당 worktree에서 실행한다. 생성·연결·전환에 실패하면 공유 체크아웃에서 구현을 계속하지 않고 원인과 필요한 조치를 알린다. worktree 생성·재사용·변경 분리·인증정보·정리의 공통 기준은 `AGENTS.md`를 따른다. `.env`를 자동 복사하지 않으며, 필요한 설정은 사용자가 로컬에서 주입한다.

업무 시작을 요청하면 AI는 현재 담당자를 조회한다. 담당자가 미지정이고 별도 담당자·미지정 요청이 없으면 작업 요청자의 Jira 계정과 배정 가능 여부를 확인해 배정하고 결과를 재조회한다. 이미 다른 담당자가 있으면 명시적인 재배정 요청 없이 변경하지 않는다. 이후 가능한 상태 전이를 조회해 `진행 중`으로 변경한다.

다른 팀원의 승인은 필수가 아니다. 필요한 경우에만 팀원에게 리뷰를 요청한다. 작성자는 MR의 변경 내용과 검증 결과를 한 번 더 확인하고, 병합해도 괜찮다고 판단하면 직접 병합할 수 있다. 작업 MR은 squash와 source branch 삭제를 적용하며, `dev` → `master` 통합은 squash하지 않는다. 구현만 끝났다고 AI가 임의로 Jira를 완료 처리하지 않는다.

## 검증

```powershell
python -m unittest discover -s scripts/jira/tests -v
```

모의 Jira로 읽기 전용 동작, 생성 결과 검증, 중복·변경된 초안 차단, 동시 재실행 기록, 타임아웃·부분 성공 처리를 확인한다. 개인 `.env` 설정 후 `--check`, 카탈로그 및 실제 승인된 업무 생성으로 실환경 동작을 별도로 확인한다. 테스트용 이슈를 승인 없이 생성하지 않는다.

기본 스프린트 모의 테스트는 활성 스프린트 1개(종료일과 무관)·활성 없음·활성 여러 개의 `default_sprint` 판단, 활성 없음일 때 가장 이른 예정 스프린트 선택, 미리보기의 스프린트 표시와 기존 승인 해시 유지를 확인한다. 2026-11-08 실제 보드에서 `--catalog`의 `default_sprint`와 활성 스프린트를 지정한 미리보기를 쓰기 0회로 확인했다. 당시 단일 활성 스프린트가 기본 스프린트로 반환되고 미리보기에 그 이름이 표시됐다. 활성 스프린트를 지정한 실제 생성·재조회 검증은 별도로 진행해야 한다.

우선순위 모의 테스트는 유형별 조회·ID/이름 해석·잘못된 값과 메타데이터 차단·승인 후 변경 차단·생성 후 및 `--verify` 불일치 검출·기존 미지정 초안의 해시 호환을 확인한다. 구현 참고 문서는 2026-10-26 Context7으로 조회한 [Jira Cloud REST API v3의 생성 필드 메타데이터](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/)다. 저장소도 REST API v3를 사용하며, 외부 Python 라이브러리 의존성은 없다. 같은 날 실제 프로젝트의 카탈로그와 우선순위 지정 미리보기를 GET 12회·쓰기 0회로 확인했다. 실제 이슈 생성으로 우선순위 저장을 검증한 것은 아니다.

2026-10-14 실환경 검증: 저장소 스크립트로 Epic `S15P31E105-23`, Story `S15P31E105-24`, Task `S15P31E105-25`를 생성했다. 제목·본문·유형·담당자 및 Epic 이름, Story/Task의 SP·Epic 연결을 재조회해 검증했다. 각 초안의 재실행이 기존 Key를 반환하고 새 이슈를 생성하지 않는 것도 확인했다. 검증 후 담당자를 지정하고 완료 상태로 정리했다. 스프린트 배정의 실환경 검증은 별도로 진행해야 한다.
