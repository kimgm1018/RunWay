## 1. 코드 스타일

- 코드 형식은 google-java-format의 AOSP 모드를 따른다. 들여쓰기 4칸(공백),
  탭 미사용, 한 줄 100자를 기준으로 하며 기계적인 배치는 도입 시 고정한 포맷터 설정을 따른다.
- 포맷터 도입 후에는 도구가 검사하는 공백·개행을 사람이 중복 지적하지 않는다.
  도입 전에는 자동 검사가 있다고 가정하지 않고 변경 범위의 형식을 확인한다.

### 1.1 네이밍

- 클래스·인터페이스·Enum·record는 `UpperCamelCase`, 메서드·변수는 `lowerCamelCase`,
  상수는 `UPPER_SNAKE_CASE`, 패키지는 소문자를 사용한다.
- 약어도 단어처럼 취급해 `userId`, `courseUrl`, `apiClient`처럼 작성한다.
- 책임이 드러나는 접미사를 사용한다.
  - HTTP 진입점: `{기능명}Controller`
  - 유스케이스: `{기능명}Service`
  - 영속성 접근: `{엔티티명}Repository`
  - 요청·응답: `{기능명}Request`, `{기능명}Response`
  - 변환: `{기능명}Mapper`
  - 비즈니스 예외: `{원인명}Exception`
- 클래스와 변수는 명사 또는 명사구, 메서드는 동사 또는 동사구로 작성한다.
- Boolean 반환 메서드는 `is`, `has`, `can`으로 시작하고, Boolean 변수와 필드는
  `active`, `enabled`, `deleted`처럼 상태가 드러나는 이름을 사용한다.
- 컬렉션은 복수형으로 작성한다. `data`, `info`, `manager`, `util`, `common`처럼
  대상이나 책임이 불분명한 이름을 피한다.
- 거리·시간·페이스를 다루는 내부 이름에는 필요하면 `distanceMeters`, `elapsedMillis`,
  `paceSecondsPerKm`처럼 단위를 드러낸다. 공개 API 필드는 명세를 따르며 임의 변경하지 않는다.
- 테스트 네이밍은 13장을 따른다.

## 2. 자동 포맷팅

자동 포맷팅은 **Spotless + google-java-format(AOSP)**을 사용한다. 빌드 설정은 `build.gradle`로
작성하고 Gradle Wrapper로 버전을 고정한다. 버전은 `backend/build.gradle`과 Wrapper 설정,
실행 명령은 [백엔드 README](../../backend/README.md)를 따른다.

초기 구성과 이후 개발에 다음 기준을 적용한다.

- 자동 수정 명령과 읽기 전용 검사 명령을 분리하고 `backend/README.md`에 플랫폼별로 기록한다.
- 완료 검증과 CI에는 읽기 전용 포맷 검사를 포함한다. 위반을 고친 뒤 다시 검사한다.
- `spotlessApply`와 `spotlessCheck`를 사용하고 검사 태스크를 `check`·`build`에 연결한다.
  CI 파이프라인 연결은 별도 인프라 구성에서 진행한다.
- IDE 설정은 자유지만 최종 형식은 저장소에 고정한 포맷터를 따른다.
- 포맷터 버전 변경은 공통 빌드 설정 변경으로 취급한다. 작업 범위 밖의 파일을 일괄 수정하지 않는다.

## 3. 패키지 구조

최상위는 계층이 아니라 **도메인 기준**으로 나눈다. 담당자 이름이나 화면 이름으로 패키지를
만들지 않는다. `domain`에는 기능별 코드를, `global`에는 공통 코드를, `infrastructure`에는
외부 연동 코드를 둔다. 이는 이 문서의 패키지 작성 기준이며 결정 대기 항목이 아니다.
아래 도메인 이름은 구조를 설명하는 일부 예시다. 다른 도메인도 같은 기준으로 추가한다.
루트 패키지는 `com.runway.backend`로 한다. 담당자 배정은 패키지 구조와 별도로 관리한다.

```text
com.runway.backend
├── domain
│   ├── auth
│   ├── user
│   ├── course
│   └── running
├── global
│   ├── config
│   ├── entity
│   ├── error
│   ├── properties
│   ├── response
│   └── security
└── infrastructure
    └── <실제 도입한 외부 연동>
```

도메인 및 내부 계층은 실제 코드가 생길 때 만든다. 빈 패키지를 미리 만들지 않는다.
예를 들어 코스 도메인을 구현하면 다음처럼 책임을 나눈다.

```text
domain/course
├── controller
├── service
├── repository
├── entity
└── dto
    ├── request
    └── response
```

- `global`: 여러 도메인이 함께 사용하는 기술적 공통 코드. `security`는 인증 필터·검증과
  공통 인가·CORS 설정을 담당하고, 로그인 등 인증 유스케이스는 `domain/auth`에 둔다.
- 설정 객체는 값을 사용하는 도메인 또는 인프라 패키지에 둔다. 여러 설정 객체가 실제 공유하는
  검증 규칙만 `global/properties`로 모은다.
- `infrastructure`: AI 서비스·외부 API 등 외부 시스템별 연결 구현. Kafka·Redis 같은
  기술별 패키지는 실제 도입한 경우에만 만든다.
- 공통화 가능성만으로 `global`에 코드를 두지 않는다. 둘 이상의 도메인에서 실제로 사용하고
  의미가 같은 경우에만 이동한다.
- 공통 코드와 최상위 패키지 변경은 구현 전에 영향 범위를 설명하고 합의한다.

## 4. 계층별 책임

### 4.1 Controller

Spring MVC의 Controller는 HTTP 경계만 담당한다. 클라이언트 API는 JSON으로 응답하며,
서버 측 화면 템플릿을 전제로 하지 않는다.

- 요청 DTO·경로·쿼리 파라미터를 받고 입력 형식과 인증 사용자 정보를 처리한다.
- Service를 호출하고 Response DTO를 반환한다.
- Repository, EntityManager, 메시지·캐시 클라이언트, 외부 API Client를 직접 호출하지 않는다.
- Entity를 생성·수정하거나 비즈니스 상태 전이를 판단하지 않는다.
- Entity를 API 응답으로 직접 반환하지 않는다.

### 4.2 Service와 도메인 객체

Service는 유스케이스 진행과 트랜잭션 경계를 담당한다.

- 비즈니스 전제와 접근 권한을 확인하고 Repository·도메인 객체·공개 컴포넌트를 조합한다.
- 객체 자체의 불변 조건과 상태 변경 규칙은 해당 도메인 객체의 의미 있는 메서드에 둔다.
  Service마다 같은 상태 전이 규칙을 중복 작성하지 않는다.
- Servlet API, `HttpServletRequest`, `ResponseEntity` 등 HTTP 표현에 의존하지 않는다.
- 구현체 교체 필요가 없는 Service에 형식적인 인터페이스를 만들지 않는다.
- Service 간 순환 의존을 허용하지 않는다. 도메인 객체는 Controller·Service·외부 Client를
  호출하지 않는다.

### 4.3 Repository

- 영속성 조회·저장만 담당한다. 비즈니스 정책 판단·외부 호출·메시지 발행을 하지 않는다.
- 소유자·공개 범위 조건을 쿼리에 반영할 수 있지만, 접근 허용 정책의 결정은 Service에서 한다.
- 단순 조회는 영속성 기술의 기본 기능을 우선하고 이름이 지나치게 길면 명시적 쿼리를 검토한다.
- 결과가 없을 수 있는 단건 조회는 `Optional<T>`를 반환한다.
- `Optional`을 Entity 필드·DTO 필드·메서드 파라미터로 사용하지 않는다.
- 기본 DB 접근은 Spring Data JPA를 사용한다. 조회 목적에 따른 선택은 9장을 따른다.

### 4.4 Infrastructure

- 외부 시스템별 설정, Client, 직렬화, 타임아웃·재시도 세부 구현을 둔다.
- Service는 가능한 한 구체 기술 대신 프로젝트가 정의한 컴포넌트나 인터페이스에 의존한다.
- 재시도는 요청의 멱등성·최대 횟수·실패 처리를 확인한 뒤 적용한다. 쓰기 요청을 무조건 재시도하지 않는다.
- AI 서비스·워치·메시지·캐시의 데이터 계약이 미정이면 연동 구현에서 임의 확정하지 않는다.

### 4.5 Spring 컴포넌트와 Lombok

- Spring 컴포넌트의 의존성은 생성자로 주입하고 의존 필드를 `final`로 선언한다.
- 반복 코드 생성에 Lombok을 사용한다. 생성자 주입에는 `@RequiredArgsConstructor`,
  로깅에는 `@Slf4j`를 사용할 수 있다. Entity에서 허용하는 애너테이션은 6장을 따른다.
- record DTO에는 Lombok을 함께 사용하지 않는다.
- `@Data`와 공개 `@Setter`는 사용하지 않는다.

## 5. DTO와 변환

### 5.1 구조·이름·검증

- 요청과 응답 DTO는 `dto/request`, `dto/response`로 분리한다.
- 요청·응답 DTO는 record를 기본으로 사용한다. 초기 구성에서 지원 Java 버전과 직렬화·검증
  호환성을 확인한다. 프레임워크 제약이 있으면 이유를 남기고 일반 클래스를 사용한다.
- DTO는 불변으로 작성한다. record가 참조하는 컬렉션 등도 외부에서 변경되지 않도록 관리한다.
  Entity는 record가 아닌 일반 클래스로 작성한다.
- `ProfileUpdateRequest`, `CourseDetailResponse`처럼 목적을 드러낸다. 이는 이름 예시이며
  명세에 없는 API·필드를 추가하라는 뜻이 아니다.
- `CommonDto`, `ResultDto`처럼 책임이 불분명한 이름을 피하고, API 목적이 다르면 필드가
  일부 같더라도 DTO를 무리하게 공유하지 않는다.
- 입력 검증에는 Bean Validation을 사용한다. 필수값·길이·형식 검증은 Request DTO에 선언한다. 경로·쿼리
  파라미터도 검증한다. 소유권·동의·상태 전이처럼 데이터 조회가 필요한 검증은 Service에서 한다.
- 허용 값·길이·단위는 계약을 따른다. 계약에 없으면 임의 상한이나 기본값으로 확정하지 않는다.

### 5.2 변환

- Entity 하나를 단순 변환하면 Response DTO의 `from` 정적 팩토리를 우선한다.
- 여러 Entity·조회 결과를 조립하는 복잡한 응답에만 도메인 내부 `mapper`와
  `{기능명}Mapper`를 추가한다.
- Mapper는 변환만 한다. DB 조회·권한 검사·상태 변경·외부 호출을 하지 않는다.
- MapStruct·MyBatis 등 매핑 도구를 임의 도입하지 않는다. 필요가 확인되면 대안·영향을
  설명하고 합의하며, 핵심 기술 선택에 해당하면 ADR을 남긴다.
- API·DB의 UUID, 시각, 단위, 결측값 의미를 변환 과정에서 보존한다. 워치 원본의 ms와
  서비스 API의 sec처럼 단위가 다르면 경계에서 명시적으로 변환하고 테스트한다.
- 외부 입력의 문자열을 무조건 Enum으로 제한하지 않는다. 워치 `quality` 등 원본 문자열
  보존이 필요한 필드는 해당 계약을 따른다.

## 6. Entity와 스키마 매핑

- Entity는 `entity` 패키지에 두고 API 계층에 노출하지 않는다.
- 테이블·컬럼·키·null 허용·길이·제약은 기준 스키마와 일치시킨다. Java 편의 때문에
  UUID를 일괄 `Long`으로 바꾸거나 필드를 임의 추가하지 않는다.
- 생성은 필수값 검증을 포함한 정적 팩토리를 우선한다. 상태 변경은 `setStatus` 대신
  `start`, `pause`, `finish`처럼 의도가 드러나는 메서드로 수행한다.
- 모든 Entity에 공통 `id`, `status`, `deletedAt`을 강제하지 않는다. 복합키·도메인별
  생명주기와 삭제 정책을 존중한다.
- 시각은 `Instant`, 날짜 자체는 `LocalDate`를 사용한다. 시간대가 별도 의미를 가지면
  해당 계약을 따른다. UTC 시각과 경과시간을 같은 타입·의미로 혼용하지 않는다.
- 감사 필드가 같고 실제 공유가 필요할 때 공통 기반 클래스를 도입한다. 아직 존재하지 않는
  `BaseTimeEntity` 등의 상속을 전제하지 않는다.

JPA Entity에는 다음 규칙을 적용한다.

- JPA용 기본 생성자는 `protected`로 제한한다.
- Entity의 Lombok은 `@Getter`, `@NoArgsConstructor(access = AccessLevel.PROTECTED)`로 제한한다.
  `@Data`, 공개 `@Setter`, `@Value`, `@EqualsAndHashCode`를 사용하지 않는다.
- `@Builder`를 기본 적용하지 않는다. 필수값·생성 규칙을 우회하지 않게 한다.
- Enum 매핑은 `@Enumerated(EnumType.STRING)`을 사용하며 실제 DB 값·제약과 일치시킨다.
- 컬렉션 필드는 빈 컬렉션으로 초기화한다.

### 6.1 DB 구조 변경

세부 규칙은 [물리 스키마·마이그레이션 문서](db-schema-convention.md)에 정리한다.
ID 생성·무결성 제약·수정 시각과 개발용 첫 Flyway 이력·번호 관리·실패 대응 기준을 정리했다.
운영 적용·복구는 별도 인프라 업무에서 확정한다. 아래 기존 결정은 유지한다.

- 테이블·컬럼·제약의 생성과 변경은 Flyway의 버전별 SQL로 관리한다. JPA의 자동 스키마 변경과
  병행하지 않는다. JPA는 `ddl-auto=validate`로 Entity와 DB 매핑을 검사하는 방향으로 구성한다.
- `docs/design/db/schema.sql`은 현재 구조를 설명하는 기준 문서이고, Flyway 파일은 실제 적용할
  변경 이력이다. 구조 변경 시 두 문서의 역할에 맞게 정합성을 유지한다.
- 이미 공유 환경에 적용한 버전별 SQL은 수정하지 않고 후속 변경 파일을 추가한다.
  번호 충돌 방지·적용 시점·실패 복구 절차는 초기 DB 구성에서 정한다.
- 현재 DB의 데이터·구조를 확인한 뒤 초기 이력을 구성한다. 빈 DB용 스키마를 기존 DB에
  그대로 실행하거나 기존 데이터를 삭제해 초기화하지 않는다.

## 7. JPA 연관관계 규칙

- 모든 연관관계의 Fetch 전략을 명시하고 `LAZY`를 기본으로 한다.
- ERD에 관계가 있다는 이유만으로 양방향 매핑을 만들지 않는다. 단방향을 우선한다.
- 양방향 관계가 필요하면 편의 메서드에서 양쪽 상태를 함께 맞춘다.
- `CascadeType.ALL`과 `orphanRemoval = true`는 생명주기가 완전히 종속된 관계에만 적용하고
  DB 삭제 제약과 함께 검토하며 MR에 이유를 남긴다.
- 외부 시스템과 공유하는 데이터는 필요하면 연관관계 대신 식별자로 참조한다. 데이터 계약을 따른다.
- Controller나 JSON 직렬화 단계에서 지연 로딩 쿼리를 실행하지 않는다.
- 반복 조회로 N+1이 발생하지 않는지 확인한다. 조회 목적에 따라 fetch join, EntityGraph,
  Projection을 검토하고 페이징·조회 건수에 미치는 영향도 검증한다.
- OSIV는 비활성화하며, 필요한 조회와 DTO 변환은 Service 경계 안에서 마친다.

## 8. 트랜잭션과 재시도

- 업무 단위의 트랜잭션 경계는 Controller가 아닌 Service에 둔다.
- 조회 메서드는 `@Transactional(readOnly = true)`,
  생성·수정·삭제 메서드는 `@Transactional`을 기본으로 적용한다.
  조회처럼 보여도 상태를 기록하는 유스케이스는 쓰기 여부를 기준으로 판단한다.
- 읽기 전용 선언만으로 여러 조회의 일관성이나 동시 실행 안전성을 보장한다고 가정하지 않는다.
  필요한 일관성 수준, DB 격리 수준·잠금·제약을 함께 검토한다.
- 하나의 유스케이스가 여러 Repository를 변경하면 최상위 Service가 원자성 범위와 실패 처리를
  소유한다. 여러 도메인이면 조정 Service와 변경 책임을 먼저 합의한다.
- 여러 행을 잠그는 경우 관련 경로의 잠금 순서를 일관되게 설계하고 교착·충돌을 검증한다.
  특정 기능의 정렬·분할 커밋 방식을 근거 없이 다른 유스케이스의 공통 규칙으로 적용하지 않는다.
- 외부 HTTP 호출·장시간 처리는 DB 트랜잭션 밖으로 분리하고, 그 사이 데이터 변경·외부 실패에
  대한 정합성 처리를 설계한다. 단순 분리만으로 일관성 문제가 해결됐다고 보지 않는다.
- 기본값과 다른 전파·격리 수준, checked exception 등을 포함한 롤백 정책은 이유와
  검증 방법을 코드 또는 작업 기록에 남기고 MR에 요약한다.
- DB 저장과 메시지 발행·캐시 갱신의 일관성은 해당 기술 도입 시 계약으로 정한다.
  개별 도메인이 임의의 보장 방식을 확정하지 않는다.
- 러닝 저장·업로드는 중복 요청, 응답 유실 후 재시도, 순서 역전, 동시 실행을 검토한다.
  “존재 여부 조회 후 저장”만으로 중복 방지가 된다고 판단하지 않는다.
- 워치 실험 업로드는 별도 계약의 영속 저장 후 성공 응답·동일 `sessionId` 재전송 규칙을 따른다.
  이를 서비스 배치 동기화 `W07`에 그대로 복사하지 않고 각각의 멱등 키·충돌·부분 실패 계약을 확인한다.

## 9. 조회 기술 선택 기준

기본 DB 접근은 Spring Data JPA를 사용한다. JPA만 사용하기 위해 DB 고유 기능이나 대량 처리
성능을 포기하지 않는다. 개발·테스트 DB는 [ADR-0011](../adr/0011-local-postgresql-postgis.md)의
PostgreSQL 17·PostGIS 3.6을 사용한다. 실제 공간 데이터 매핑은 ERD 확정 후 해당 기능에서 확인한다.

| 상황 | 기본 선택 |
| --- | --- |
| 일반 CRUD·단순 조건 조회 | Spring Data JPA 파생 쿼리 |
| 고정된 조인·조회 최적화 | JPQL, fetch join, EntityGraph 또는 DTO Projection |
| 선택 조건이 조합되는 동적 조회 | Spring Data JPA Specification 우선 검토 |
| PostGIS 공간 질의 등 DB 고유 기능 | 지원 매핑·함수 또는 Native Query 검토 |
| 측정 데이터 대량 적재·일괄 갱신 | JPA 처리와 비교 후 JDBC batch 검토 |

- QueryDSL은 자동 도입하지 않는다. 기존 방식으로 유지하기 어려운 쿼리가 확인되면 합의한다.
- Native Query·직접 SQL·배치 처리 선택 시 기존 방식이 부적합한 이유와 검증 방법을 기록한다.
- 값은 파라미터 바인딩을 사용한다. 정렬 컬럼 등 바인딩할 수 없는 요소는 허용 목록으로 제한하고
  클라이언트 입력을 SQL에 직접 이어 붙이지 않는다.
- JPA와 직접 SQL로 같은 데이터를 변경하면 영속성 컨텍스트와 DB 상태 불일치를 검토한다.
- 공간 데이터의 좌표계·좌표 순서·거리 단위와 실제 DB 쿼리 결과를 검증한다.

## 10. API 응답과 예외 처리

- 공개 API 계약은 API 명세가 관리한다. Controller마다 임의 응답 구조를 만들지 않는다.
- 성공 래퍼, 페이지네이션, 공통 오류 필드·HTTP 상태는 현재 API 초안의 미확정 항목이다.
  다른 서비스의 응답·커서·오류 규약을 확정값으로 가져오지 않는다.
- 공통 오류가 확정되면 공통 오류 응답 타입과 의미 있는 오류 코드로 통일한다.
  코드 이름은 `UPPER_SNAKE_CASE`로 작성하고 상태·사용자용 메시지 매핑을 한곳에서 관리한다.
- Service의 비즈니스 예외는 전역 예외 처리기에서 HTTP 상태·오류 응답으로 변환한다.
  Controller마다 메시지를 직접 만들거나 예외를 성공 응답으로 숨기지 않는다.
- 예상하지 못한 예외의 스택·SQL·외부 응답 원문·민감정보를 사용자에게 반환하지 않는다.
- 없는 리소스와 노출하면 안 되는 리소스의 처리 차이는 확정된 API 계약을 따른다.
- 새로운 공개 오류·응답 정책이 필요하면 API 명세를 먼저 합의·갱신한다.

## 11. 도메인 간 참조와 공통 코드

- 다른 도메인의 Entity 필드를 직접 변경하지 않는다. 소유 도메인의 공개 메서드 또는 합의한
  유스케이스 경계를 사용한다.
- 다른 도메인의 Repository를 사용하는 교차 도메인 트랜잭션은 소유권·조정 Service·의존 방향을
  먼저 합의한다. 역할 분담 문서의 미정 항목은 현재 Jira와 팀 확인을 근거로 갱신한다.
- 순환 의존을 공통 Service로 숨기지 않는다. 유스케이스 경계를 재검토하며 이벤트가 필요하면
  별도 기술·계약 합의를 거친다.
- 공통 DTO·오류 코드·DB 스키마·이벤트 계약 변경은 공통 지침과 백엔드 지침의 영향 검토를 따른다.
- 인증 설정은 기본적으로 인증을 요구하고, 계약상 공개인 API만 명시적으로 허용하는 방향으로
  구성한다. 구체 인증 수단과 공개 경로는 인증 계약 확정 후 적용한다.
- 인증 성공만으로 리소스 접근을 허용하지 않는다. 소유자·참가자·공개 범위·동의 및 철회 상태를
  유스케이스에서 확인한다. 요청 본문의 사용자 ID를 인증된 사용자로 신뢰하지 않는다.
- 건강·GPS 접근 정책을 도메인마다 다르게 구현하지 않는다. 정책은 해당 계약에 두고 공통화할
  구현이 실제 확인되면 소유권과 인터페이스를 합의한다. 존재하지 않는 필터·코덱을 전제하지 않는다.

## 12. 로깅과 민감정보

- 비밀번호, 토큰, 쿠키, OAuth 코드, 인증 헤더, 실제 개인정보·건강 수치·GPS 좌표와 이동 경로를
  로그에 남기지 않는다. 요청·응답 객체 전체를 자동 출력하지 않는다.
- `System.out.println` 대신 프로젝트에서 정한 표준 로깅 도구를 사용한다.
- 흐름 추적에는 최소한의 요청 추적 ID와 처리 결과를 사용한다. 사용자·기기·세션 ID도 개인과
  연결될 수 있으므로 안전한 값이라고 가정하지 않고 필요성·마스킹·보관 정책을 검토한다.
- 예외는 처리 책임이 있는 경계에서 기록하고 같은 예외를 여러 계층에서 중복 로깅하지 않는다.
- 테스트·문서 예시는 합성 데이터를 사용한다. 실제 건강/GPS 자료를 AI 질문·테스트 fixture에 넣지 않는다.
- AI의 실제 인증정보 파일 접근 금지와 예시 설정 사용은 루트 지침을 그대로 따른다.

## 13. 테스트 작성 기준

백엔드 자동 테스트는 JUnit Jupiter 기반 단위 테스트, Spring MVC API 테스트,
Testcontainers 기반 DB 통합 테스트로 구성한다. 라이브러리 버전은 Spring Boot가 관리하는
호환 조합을 우선하며, 실제 설정·실행 명령은 초기 구성에서 확인한다.
플랜·리뷰 산출물과 생략 조건은 백엔드 지침을 따른다.

- DB 통합 테스트는 실제 사용할 DB와 필요한 확장을 갖춘 컨테이너에서 수행한다.
  PostgreSQL·PostGIS 대상 테스트에는 해당 기능이 제공되는 이미지를 사용한다.
- 개발 PC와 CI의 Docker 사용 가능 여부는 초기 구성에서 확인한다. 컨테이너를 실행하지 못한
  필수 DB 테스트는 미실행으로 보고하고 다른 DB의 성공으로 대신하지 않는다.
- 초기 구성에서는 테스트 환경과 기본 실행을 검증한다. ERD 변경이 정리되기 전에 도메인
  Entity·테이블을 임의 생성하지 않으며, 실제 기능 테스트는 각 기능 구현과 함께 추가한다.

- 테스트는 준비·실행·검증이 드러나게 작성한다. 내부 호출 횟수만 확인하지 말고 외부에서
  관찰할 결과·오류·저장 상태를 검증한다. 구현을 복사해 기대값을 계산하지 않는다.
- 클래스명은 단위 테스트 `{대상}Test`, 통합 테스트 `{대상}IntegrationTest`를 기본안으로 한다.
  메서드명은 `조건_행동_기대결과`처럼 시나리오가 드러나게 작성한다.
  예: `동일세션재전송_업로드_저장건수가늘지않는다`는 의도를 설명하는 이름 예시다.
- 테스트 간 실행 순서·실제 시각·외부 네트워크에 의존하지 않는다. 시간·외부 응답은 제어 가능한
  경계로 분리하고 DB 테스트는 데이터 격리·정리 방법을 둔다.

| 구분 | 확인할 내용 | 놓치지 말아야 할 검증 |
| --- | --- | --- |
| 단위 | 도메인 규칙·상태 전이·계산·Service 분기 | 정상·경계·잘못된 입력·실패 후 상태. 외부 의존은 필요한 경계만 대체 |
| 통합 | Repository·매핑·제약·트랜잭션·실제 컴포넌트 조합 | 실제 사용할 DB의 기능·롤백·중복·동시 실행. Mock만으로 DB 동작을 검증했다고 하지 않음 |
| API | 요청 검증·인증·인가·직렬화·오류 변환 | 정확한 HTTP 상태·필드·오류 코드, 타인 자원 접근 거부. Service를 대체했다면 저장 검증과 구분 |

- UUID·시간·단위·null 의미와 워치 재전송·응답 유실·순서 역전은 해당 기능의 테스트에 포함한다.
- PostgreSQL·PostGIS 고유 동작은 해당 DB 환경에서 검증한다. 대체 DB의 성공만으로 동일하게
  동작한다고 판단하지 않는다. 동시성 테스트는 실제 교차 실행과 커밋 결과를 확인한다.
- AC와 테스트의 연결을 유지하고 기대값 변경을 근거 없이 통과 수단으로 사용하지 않는다.
  테스트 변경 확인·기록 절차는 백엔드 지침을 따른다.
- 자동화할 수 없는 항목만 대체 검증을 사용한다. 대상·준비·행동·정확한 통과 조건·증거·한계를
  적고 미실행을 통과로 보고하지 않는다. 환경 부족만으로 필수 테스트를 문서 검토로 대체하지 않는다.
- 테스트 도구와 실행 명령은 백엔드 README를 따른다. 각 기능에서 필요한 단위·통합·API 테스트는
  위 기준으로 선택한다. 커버리지 수치만으로 실효성을 판단하거나 모든 테스트에 전체
  애플리케이션 기동을 강제하지 않는다.

## 14. AI 생성 코드 적용 규칙

AI가 생성한 코드도 같은 규칙을 적용한다. 작업 범위·보안·문서 우선순위는 루트 지침,
백엔드 구현의 계획·검증·리뷰는 백엔드 지침을 따른다. 이 문서에 절차를 중복 정의하지 않는다.
개발 전 규칙·양식 정비만 하는 작업에는 별도 플랜·리뷰 파일을 만들지 않고 문서 정합성을 검토한다.

## 15. 초기 구성과 후속 확인 범위

도메인별 패키지 구조, 계층의 책임, 네이밍과 테스트 작성 기준은 앞의 본문을 따른다.
아래는 작성 규칙을 보류하는 목록이 아니라 구성한 기반과 남은 검증·후속 구현 범위다.
설정이 있다는 이유만으로 실행 검증까지 통과했다고 취급하지 않는다.

| 항목 | 무엇을 확인하는가 |
| --- | --- |
| Java·Spring Boot 및 Gradle 버전 | Java 21·Boot 4.1.1·Gradle 9.8.2를 설정했다. 배포판·명령은 README 참조. |
| 자동 포맷 검사 | Spotless·AOSP와 `check`·`build` 연결을 구성했다. CI 파이프라인은 별도 업무다. |
| DB 연결과 JPA 설정 | PostgreSQL 17·PostGIS 3.6 개발·테스트 환경과 `validate`·OSIV 비활성화를 설정했다. Entity 매핑은 ERD 확정 후 검증한다. |
| Flyway 초기 이력 구성 | V1으로 기준 스키마를 설치하고 재적용·보존·기존 DB 거부·변조 감지·실패·구조 정합성을 격리 DB에서 검증한다. 개발 절차는 DB 규칙 참조, 운영 적용은 별도 업무다. 기존 DB를 초기화하지 않는다. |
| DTO·반복 코드·입력 검증 설정 | record·Lombok·Bean Validation 의존성과 테스트 전용 검증 사례를 구성했다. 제품 API 계약을 확정한 것은 아니다. |
| 테스트 실행 환경 | JUnit Jupiter·MVC·Testcontainers 테스트를 구성했다. 실제 Docker 실행과 전체 빌드 성공을 완료 조건으로 확인하며 미실행은 별도 기록한다. |

선택한 도구·버전·실행 명령은 실제 설정과 `backend/README.md`에 기록하고, 이 문서의 관련
설명도 맞춘다. 핵심 기술 선택은 ADR 운영 규칙을 따른다. 설정하지 않은 도구를 설치 완료로
기록하지 않는다.

인증 방식·응답 형식·페이지네이션은 API 설계에서, 워치 업로드·AI 연동·동시 실행 처리는 해당
기능 설계에서 다룬다. 구체적으로는 로그인 유지 방법, 목록을 나누어 조회하는 방법, 같은 기록을
두 번 받았을 때의 처리 등을 정하는 일이다. 이들은 컨벤션 전체의 확정 조건이 아니며, 해당 기능을
구현할 때 관련 계약을 확인한다. 메시지·캐시처럼 아직 필요성이 정해지지 않은 기술도 컨벤션의
필수 결정 목록에 미리 넣지 않는다.
