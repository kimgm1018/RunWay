# ADR-0009: DB 구조 변경 이력은 Flyway로 관리한다

## 맥락

현재 기준 스키마는 빈 DB에 초기 구조를 생성하기 위한 SQL이다. 개발·배포 후에도 기존 데이터를
유지하면서 구조를 변경하고, 환경마다 어떤 변경까지 적용했는지 관리할 방법이 필요하다.

## 결정

DB 구조 생성·변경 SQL의 버전과 적용 이력은 Flyway로 관리한다. JPA의 자동 스키마 변경과
병행하지 않고, JPA는 `ddl-auto=validate`로 매핑을 검사하는 방향으로 구성한다.
현재 구조를 설명하는 기준 스키마와 실제 변경 이력인 Flyway SQL의 정합성을 유지한다.

합의 근거: 작업 요청자가 Flyway 사용 의사를 밝힌 뒤, 본 업무 대화에서 제안한
Gradle(`build.gradle`)·JPA·Flyway 조합에 “좋은 것같아”로 동의했다.
이 결정은 도구 선택이며 DB에 SQL을 실행하거나 기존 데이터를 변경한 것은 아니다.

## 고려한 대안

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| Flyway로 버전별 SQL 관리 (선택) | 적용 순서·이력을 관리하고 환경별 변경을 추적할 수 있음 | 변경 SQL 작성·번호 관리·적용 실패 대응이 필요 |
| 변경 SQL을 사람이 직접 적용·기록 | 별도 도구 도입 없이 시작 가능 | 적용 누락·순서 차이와 환경별 이력을 직접 관리해야 함 |
| JPA 자동 스키마 변경 | 초기 실험의 구조 생성이 간단함 | 검토된 변경 SQL과 버전별 적용 이력을 관리하려는 목적에 맞지 않음 |

Liquibase 등 다른 마이그레이션 도구와의 상세 비교는 수행하지 않았다.

## 결과

- **얻는 것**: 데이터 접근과 스키마 변경 책임 분리, DB 변경 이력 추적
- **감수하는 것**: 적용된 변경 파일의 보존과 배포 시 검증 필요. 자동 데이터 복구를 보장하지 않음
- **후속 작업**: DB 버전과 맞는 Flyway 의존성 구성, 기존 DB 유무·데이터 확인, 초기 이력과
  번호 관리·실행 시점·복구 절차 정의, 빈 DB 및 기존 구조에서의 적용 테스트.
  초기 스키마를 기존 DB에 그대로 실행하거나 적용 이력을 임의로 조작하지 않는다.
